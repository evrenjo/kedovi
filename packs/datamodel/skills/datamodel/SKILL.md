# datamodel: 데이터 설계 (테이블 정의서 · ERD)

양식 · 뷰어 · 검사는 킷이 준다. 이 스킬은 내용을 채우는 순서다. 각 단계에서 정할 것은 사용자에게 **하나씩** 묻고, 권장안을 첫째 선택지로 둔다.

| 파일 | 내용 |
|---|---|
| `packs/datamodel/assets/erd/template.md` | 정의서 견본 (스키마 한 파일: 「### 스키마.테이블 논리명」 + 설명 줄 + 컬럼 표) |
| `packs/datamodel/assets/erd/` 의 `src/` · `erd.css` · `ddl.js` · `elk.bundled.js` | ERD 뷰어 (문서 사이트를 만들 때 `assets/erd/` 로 들어간다. 기획 repo 에 따로 두지 않는다) |
| `packs/core/bin/docs-site.js` | `kedovi docs build` : 정의서가 든 폴더마다 `<폴더>/erd.html` 을 만든다 |
| `packs/datamodel/bin/check-datamodel.js` | `kedovi datamodel check` : 참조 · 기본키 · 중복 · 표 형식 · 컨벤션 · 기능 ID 대조 |

## 1. 진행 방식 합의

먼저 아래를 정한다. 기획 repo 에 이미 정해 둔 것이 있으면 따른다.

- **대상**: 어떤 저장소인가 (서비스별 스키마 · 한 DB · 여러 DB). 차세대면 AS-IS 테이블을 옮기는지 새로 짓는지.
- **근거 문서**: 요구사항 · 기능정의 · 결정 문서의 위치. 테이블 · 컬럼은 기능 ID · 결정 ID 를 근거로 만든다. **근거 없는 테이블 · 컬럼을 지어내지 않는다.** 필요해 보이지만 근거가 없으면 "근거 없음" 으로 묻는다.
- **산출물 위치**: 기획 repo 의 데이터 설계 폴더(뼈대 기본 `40-data/`, 옛 뼈대 `06-data/`). `README.md` = 엔티티 목록 · 컨벤션 표 · 결정, `<스키마>.md` = 스키마마다 한 파일.
- **순서**: 컨벤션 → 엔티티 목록 → 스키마별 정의서 (화면설계보다 먼저: 화면이 보여 줄 데이터와 저장 구조가 먼저 정해져야 한다).

## 2. DB 컨벤션 정하기

프로젝트마다 다르다. 킷은 값을 강제하지 않는다. 이미 운영 중인 DB 나 기존 코드가 있으면 **기존 테이블 몇 개를 열어 관례를 먼저 확인**하고 그 값을 권장안으로 둔다. 없으면 `packs/db/rules/60-data-modeling.md` 의 기본값을 권장안으로 둔다 (db 팩이 없으면 아래 표의 권장안).

| 질문 (하나씩) | 권장안 (관례가 없을 때) | 저장할 곳 `vars.datamodel.` |
|---|---|---|
| DB 종류 | 프로젝트 스택의 DB | `dialect` (postgresql · mysql · mariadb · oracle · mssql · sqlite. sqlite 면 타입을 INTEGER · TEXT · REAL · BLOB · NUMERIC 으로 검사) |
| 이름: 대소문자 · 단수/복수 · 접두어 | snake_case · 단수 · 접두어 없음 | `naming` · `tablePrefix` |
| 기본키 타입 | 64비트 정수 대리키 (외부 노출 · 여러 곳에서 만들면 UUID) | `pkType` |
| 공통 감사 컬럼 | 생성 · 수정 일시 (주체 컬럼은 요구가 있을 때) | `auditColumns` |
| 삭제 방식 | 물리 삭제 (되살리기 요구가 있으면 기간을 정한 소프트 삭제) | `softDelete` |
| 시점 타입 | 시간대가 붙은 형식 (PostgreSQL `timestamptz`) | `timeType` |
| 금액 · 수량 타입 | 고정 소수 (`numeric` · `decimal`) | `moneyType` |
| 코드값(enum) 방식 | 운영 중 늘어나면 코드 테이블, 안 바뀌는 작은 집합은 문자열 + CHECK | `enumStyle` |
| 외래키를 DB 에 걸지 | 건다 (다른 DB · 서비스로 나뉘어 못 걸면 그 사실과 대신 지키는 법을 적는다) | `fkInDb` (Y · N) |

- 답은 워크스페이스 `workspace.json` 의 `vars.datamodel` 에 적고 `kedovi sync` 한다. 검사기와 Export DDL 이 읽는다.
- 같은 내용을 데이터 설계 폴더 `README.md` 의 컨벤션 표에도 적는다 (기획자가 읽는 쪽). 정한 것은 결정 ID 를 단다.
- 기능 ID 머리말은 `vars.datamodel.functionIds` (비우면 `vars.screens.functionIds`). 기능 대조 검사가 쓴다.

## 3. 엔티티 목록

데이터 설계 폴더 `README.md` 에 엔티티 목록 표를 둔다.

| 엔티티 | 테이블 | 기능 ID | 비고 |
|---|---|---|---|

- 기능정의의 기능 ID 를 모두 대조한다: **저장하는 기능마다 테이블**이 있어야 한다. 저장하지 않는 기능(조회만 · 외부 API 실시간 등)은 테이블 칸에 「없음」 과 이유를 적는다. 검사는 「없음」 과 같은 줄의 기능을 세지 않는다.
- 진행 방식이 스프린트(AGENTS.md 「진행 방식」)이면 이번 스프린트(`handoffs/PLAN.md` 「이번 스프린트」) 기능의 테이블만 만든다. 나머지 기능은 한 줄에 모아 테이블 칸에 「다음 스프린트」 로 적는다 (검사가 세지 않는다). 나중에 붙일 기능 때문에 지금 테이블 · 컬럼을 미리 만들지 않는다.
- 한 기능이 여러 테이블을 쓰면 여러 줄로.

## 4. 스키마별 테이블 정의서

`template.md` 를 `<스키마>.md` 로 복사해 시작한다.

- 제목: 「### <스키마>.<테이블> <논리명>」. 이름은 2단계 컨벤션대로.
- 설명 줄: 한 줄 설명 + 꼬리표 `기능: FN-…` · `결정: …` · `파티션: …` · `보존: …` · `영역: …`(ERD 주제 영역, 테이블이 많으면 모든 테이블에) · `분류: 코드`(값 목록 테이블) · `고정 스키마: <근거>`(프레임워크가 만들어 이름 · 컬럼을 바꿀 수 없는 테이블: 기본키 없음은 ⚠, 이름 · 공통 컬럼 · 타입 규칙은 건너뜀) · `ERD: 선 숨김`(감사 · 소유자처럼 많이 참조되는 테이블). 쓰는 기능이 없으면 「기능: 없음 (이유)」, 공통 컬럼을 빼면 「공통 컬럼: 없음 (이유)」.
- 컬럼 표: `컬럼 | 논리명 | 타입 | 널 | 키 | 참조 | 설명`. 널은 Y 면 허용, 키는 PK · FK · UK 를 쉼표로, FK 의 참조는 `<스키마>.<테이블>.<컬럼>`.
- DB 외래키를 걸지 않고 앱이 지키는 참조(다른 서비스 · 다른 영역 · 보관 정리 때문)는 **논리 참조**로 적는다: 키에 FK 없이 참조 칸에 `논리: <스키마>.<테이블>[.<컬럼>]`. ERD 는 켜면 점선으로 그리고, 검사는 대상이 없을 때만 ⚠. 설명 칸에 「논리 참조: …」 로 적지 않는다.
- JSON 컬럼을 제한하는 프로젝트면 `vars.datamodel.jsonReason` 을 Y 로 두고 설명 칸에 「JSON 허용: <사유>」 를 적는다.
- 타입은 정한 DB 종류의 타입으로 적는다 (Export DDL 이 그대로 옮긴다).
- 인덱스 · 제약은 컬럼 표 뒤에 따로 적어도 된다 (ERD 에는 넣지 않는다). 인덱스는 실제 쿼리로 필요를 확인한 뒤 정한다.
- 정해지지 않은 것은 설명 칸에 「미정: …」 로 남기고 사용자에게 묻는다.

## 5. ERD 생성 · 검사 · 사이트 반영

```
kedovi docs build <기획 repo>       # docs-site/ 와 <폴더>/erd.html 을 다시 만든다 (정의서를 고칠 때마다)
kedovi datamodel check <기획 repo>  # ✖ 가 없어야 한다
```

- ERD 는 정의서에서 생성한다. **HTML 을 손으로 고치지 않는다.** Pages 를 켠 repo 는 `docs-site/` 를 커밋한다 (기획 repo pre-commit 이 어긋나면 막는다).
- 문서 사이트: 데이터 설계 묶음의 첫 항목(폴더 README 쪽)이 개요가 되어 맨 위에 스키마 · 테이블 수와 「▶ ERD 보기」 를 보이고, 묶음 제목 옆 ▶ 도 ERD 로 간다. 뷰어의 「← 문서」 는 그 개요로 돌아간다.
- 뷰어의 Export ▾ 로 SQL DDL(검토용) · SVG · A4 가로 PDF 를 받는다. **DDL 은 검토용이다.** 실제 스키마 변경은 마이그레이션 도구로 한다 (`packs/db/rules/20-schema-change.md`, db 팩이 있을 때).
- 결과를 사용자에게 알릴 때 스키마 · 테이블 · 관계 수와 검사 결과(✖ · ⚠ 줄)를 그대로 옮긴다.
