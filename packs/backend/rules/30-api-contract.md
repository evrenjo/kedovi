## 1. 먼저 기존 계약을 찾는다 (새로 만들지 않는다)

코드를 쓰기 전에 아래를 **실제 파일에서** 확인하고, 찾은 형태를 그대로 따른다. 확인한 파일은 보고에 적는다.

| 볼 것 | 어디서 |
|---|---|
| 성공 응답 모양 (봉투 유무, 목록·페이지 형태, 날짜·금액 표기) | 같은 도메인·옆 도메인의 기존 엔드포인트 3~5개 |
| 오류 응답 모양 (필드, 오류 코드 체계, 검증 오류 목록, 추적 ID 포함 여부) | 전역 오류 처리기(예외 → 응답 변환 한 곳) |
| 예외 계층 (업무 거부·없음(404)·충돌(409)·권한) | 전역 오류 처리기가 잡는 예외 목록 |
| 메시지 방식 (i18n 파일·키 형식·조회 함수) | 메시지 리소스 파일과 그것을 부르는 코드 |
| URL·버전·페이지·정렬 파라미터 규칙 | 라우트 정의 · API 문서(OpenAPI 등) |
| 인가 방식 (역할·권한 매핑, 소유자 확인 헬퍼) | 기존 엔드포인트의 인가 코드, 보안 설정 |

- **만들기 전에 이미 있는지 찾는다** — 같은 일을 하는 엔드포인트·헬퍼가 있으면 그것을 쓰거나 고친다.
- **화면이 쓰는 API 는 계약을 정하기 전에 그 화면 정본(프로토타입 · 화면설계서)과 대조한다** (`kedovi screens inventory <화면 ID>` 의 요소 · 데이터 원천). 정본에 보이는 값 · 동작(계좌별 상태 · 수량 · 건수 · 필터 등)을 계약이 주지 못하면 계약을 넓히거나 사용자에게 묻는다. 계약에 맞춰 화면을 줄이지 않는다.
- 🚫 새 응답 봉투·새 오류 코드 체계·새 예외 계층을 들여오지 않는다. 불편해도 따르고, 바꾸자는 제안은 따로 사람에게.
- 관례가 섞여 있으면 **가장 최근·가장 많이 쓰인 쪽**을 따르고 그 사실을 보고한다.
- **관례가 전혀 없는 신규 프로젝트**일 때만 안을 제시한다. 이때 표준 형식(RFC 9457 Problem Details)이 기본 후보다 — `packs/backend/docs/api-reference.md`.

## 2. 인가 (모든 엔드포인트)

- **객체 단위** — 경로·쿼리·본문에 들어온 ID 마다 "이 사용자가 이 행에 접근할 수 있는가"를 서버에서 확인한다. 목록 조회는 쿼리 조건에 소유 범위를 건다(가져온 뒤 거르지 않는다).
- **기능 단위** — 관리 기능·쓰기 기능은 역할·권한을 확인한다. 화면에서 버튼을 숨긴 것은 인가가 아니다.
- **속성 단위** — 요청은 **허용된 필드만** 받는다(대량 할당 금지: 역할·소유자·상태·가격 같은 필드를 클라이언트 값으로 덮지 않는다). 응답은 호출자가 볼 수 있는 필드만 싣는다.
- 요청에서 ID 를 꺼내 바로 조회하지 않는다 — 프로젝트에 **권한을 확인하며 조회하는 헬퍼**가 있으면 반드시 그것을 거친다.
- 기본은 거부. 없는 행과 권한 없는 행을 어떻게 응답(404/403)하는지는 기존 관례를 따른다.
- 대량 호출로 해가 되는 업무 흐름(가입·쿠폰·예약·발송 등)은 기능 인가와 별도로 호출 한도·중복 방지를 둔다.

## 3. 입력 검증

- 경계(진입점)에서 검증하고 **필드 단위 오류**로 돌려준다 — 기존 오류 형식 그대로.
- **허용 목록**으로 검증한다(타입·형식·열거값·범위). 금지 목록으로 걸러내지 않는다. 정규식은 전체 일치(`^…$`)로.
- 형식 검증(구문)과 업무 검증(의미: 시작일 ≤ 종료일, 참조 행 존재)을 둘 다 한다.
- 검증은 SQL·HTML 주입 방어를 대신하지 않는다 — 그건 바인딩·출력 인코딩이 한다.
- 문자열 길이·숫자 정밀도는 **저장 컬럼과 같게**. 없으면 초과 입력이 DB 오류로 500 이 된다.
- 생성·수정 입력에 **같은 제약**을 둔다 (한쪽만 있는 비대칭이 흔한 결함).
- 서비스 안에서만 판정할 수 있는 오류도 같은 필드 오류 형식으로, **트랜잭션이 롤백되는 방식**으로 던진다.
- 요청 크기·배열 길이·업로드 크기에 상한을 둔다. 클라이언트 검증은 편의일 뿐 서버 검증을 대신하지 않는다.

## 4. 상태 코드와 오류

- 업무 거부(4xx)와 예상 못 한 오류(5xx)를 **다른 예외**로 구분한다. 언어 기본 예외를 업무 거부로 쓰지 않는다. 예상된 업무 거부를 500 으로 내지 않는다 — 5xx 는 "코드가 이 입력을 처리하지 못했다" 는 신호로 감시된다.
- 예외를 잡는 것은 **그 자리에서 복구·정리(자원 해제·보상·롤백)할 수 있을 때만**. 아니면 잡지 말고 전역 처리기로 올린다. 잡아서 삼키거나 로그만 남기고 계속 가지 않는다.
- 응답 본문에 스택트레이스·SQL·내부 경로·프레임워크 버전·하위 예외 원문을 싣지 않는다 — 로그로. 오류 응답에 추적 ID 를 싣는 관례가 있으면 따른다.
- 상태 코드는 뜻대로 (자세한 표는 `packs/backend/docs/api-reference.md`):
  - 검증 실패 400(관례상 422), 인증 없음 401, 권한 없음 403, 없음 404, 상태 충돌·동시 수정 409, 조건부 요청 불일치 412, 한도 초과 429.
  - 허용 안 된 메서드 405, 너무 큰 본문 413, 받지 않는 형식 415.
- 권한 없음과 없음 중 무엇을 먼저 알릴지(존재 자체를 숨길지)는 기존 관례를 따른다. 새로 정하면 모든 엔드포인트에 같게.

## 5. 사용자 메시지

- 사용자 노출 문구 = 예외 메시지 · 검증 오류 · 대량 작업 실패 사유 · 응답 메시지. 전부 프로젝트 메시지 체계로.
  - 키는 기존 형식을 따르고, 같은 뜻이면 재사용한다. 지원하는 **모든 로케일에 동시에** 등록한다.
  - 동적 값은 치환 인자로(문자열 연결 금지). 식별자 숫자는 문자열로 넘긴다(로케일 포맷이 천 단위 구분자를 넣는 경우가 있다).
- 로그 메시지는 i18n 대상이 아니다.

## 6. 목록·페이지

- 모든 목록은 **페이지 크기 기본값과 최댓값**이 있다. 무제한 조회 파라미터를 받지 않는다.
- 정렬은 **결정적**으로 — 유일 키를 마지막 정렬 기준에 더한다(안 그러면 페이지 사이에 행이 중복·누락된다).
- 최댓값을 넘는 요청은 최댓값으로 줄이거나 400 — 기존 관례대로. 음수·0 같은 이상값은 거부한다.
- 커서·페이지 토큰은 **위치만** 뜻한다. 토큰을 가졌다고 인가를 건너뛰지 않고, 토큰을 받은 뒤 다른 조건이 바뀌면 거부한다.
- 방식(번호·오프셋 / 커서)은 기존 관례. 새로 정할 수 있고 데이터가 크거나 자주 바뀌면 불투명 커서가 낫다.

## 7. 값 표현·캐시

기존 응답에 이미 정해진 표현이 있으면 그것을 따른다. 새 필드를 만들 때만 아래가 기본이다.

- **시각** — RFC 3339 문자열, 기준 시간대를 명시(UTC `Z` 권장). 날짜만인 값과 시각을 구분한다.
- **금액** — 부동소수(float·double) 금지. 십진 문자열·십진 타입 + 통화 코드(ISO 4217). 반올림 규칙은 한 곳에서.
- **큰 정수 ID** — JSON 숫자로 안전한 범위(±2^53−1)를 넘을 수 있으면 문자열로 싣는다(자바스크립트 클라이언트가 조용히 반올림한다).
- **null 과 빈 값** — 없음(`null`·필드 생략)과 빈 목록·빈 문자열의 뜻을 섞지 않는다. 한 API 안에서 같은 규칙.
- **캐시** — 사용자별·민감한 응답은 `Cache-Control: no-store`(또는 `private`) 를 기존 설정대로 붙인다. 공유 캐시가 인증된 응답을 다른 사용자에게 주지 않게.
- **오래 걸리는 작업** — 요청 시간 안에 끝나지 않는 작업은 동기 응답으로 버티지 않는다. 202 + 상태 조회 경로처럼 비동기로 돌리고, 시작 전에 할 수 있는 검증은 다 한다.

## 8. 재시도와 멱등성

- GET·PUT·DELETE 는 멱등하게 구현한다(같은 요청 반복 = 같은 결과).
- 클라이언트·게이트웨이·메시지 큐가 **재시도할 수 있는 생성·결제·발송**은 멱등 키(요청 ID)나 자연 키 유니크 제약으로 중복 실행을 막는다.
  - 같은 키 재요청엔 처음 결과를 돌려준다. 같은 키에 다른 본문은 거부한다.
  - 키 기록과 본 처리는 **한 트랜잭션**에 넣는다(기록만 남거나 처리만 남는 경우를 없앤다).
  - 규약·상태 코드는 `packs/backend/docs/api-reference.md`.
- 상태를 바꾸는 동작을 GET 으로 만들지 않는다 — 캐시·미리 가져오기·크롤러가 부른다.

## 9. 기존 API 를 바꿀 때 — 깨지 않고 더한다

- 안전: 선택 필드·새 엔드포인트·새 선택 파라미터 추가.
- **깨짐**: 필드 삭제·이름·타입·의미 변경, 필수로 바꾸기, 상태 코드·오류 형식 변경, 열거값 추가(클라이언트가 모르는 값을 받을 수 있는 경우). 깨는 변경은 사람 승인 → 새 버전 또는 폐기 공지·유예 기간.
- 버전을 어디에 싣는지(경로·헤더·쿼리)는 기존 관례. 가이드마다 다르므로 새로 고르지 않는다.
- 응답에 **모르는 필드가 와도** 클라이언트가 깨지지 않게, 서버도 모르는 요청 헤더(추적 헤더 등)로 요청을 거부하지 않는다.
- 이 저장소 밖 소비자(다른 팀·앱·배치)가 있는지 모르면 **있다고 가정**한다. 생성 클라이언트·API 문서가 있으면 재생성 필요를 알린다. **생성된 코드는 손으로 고치지 않는다** — 원본(스펙·스키마)을 고치고 다시 만든다.

## 10. 새 엔드포인트 체크

- [ ] 기존 응답·오류 형식을 확인했고 그대로 따랐다
- [ ] 인가: 기능 + 객체(ID 마다) + 속성(허용 필드만 입출력)
- [ ] 입력 제약 = 컬럼 길이·정밀도, 생성·수정 대칭, 크기 상한
- [ ] 목록이면 페이지 상한·결정적 정렬 / 재시도될 쓰기면 멱등 / 상태 변경은 GET 이 아님
- [ ] 인증·쿠키·CORS·요청 한도 등 보안 설정이 새 경로에도 걸린다 (「백엔드 보안」)
- [ ] 사용자 문구가 메시지 체계에 모든 로케일로 등록됐다
- [ ] 권한·엔드포인트 등록 절차가 프로젝트에 있으면 그것까지 (project 팩 룰), API 문서·생성 클라이언트 재생성 필요를 알렸다
