## 레이어 책임 · 공통 로직 추출

레이어 파일(컨트롤러 · 서비스 · 저장소 · 설정 · 모듈 · 화면 컴포넌트 · 라우트 핸들러)에는 **그 레이어의 일만** 둔다. 도우미 메서드 · 상수를 줄줄이 늘어놓아 레이어 파일이 다른 일을 떠안게 하지 않는다.
**도우미 메서드** = 그 클래스 · 파일 안에서만 불리는 메서드 · 함수다. 접근 제한자와 상관없다: `public` 으로 바꿔 자기만 부르는 것도 도우미이고, 필드의 `private` 은 이 규칙과 관계없다 (필드는 언어 규칙대로).

| 레이어 | 하는 일 |
|---|---|
| 진입점 (컨트롤러 · 라우트 · 핸들러) | 입력 해석 · 검증 연결 · 위임 · 응답 변환 |
| 서비스 (유스케이스) | 흐름 조율 · 트랜잭션 경계 |
| 저장소 | 데이터 접근 |
| 설정 · 모듈 | 조립 (빈 · provider 정의) |
| 화면 컴포넌트 | 표시 · 이벤트 연결 |

- **도우미 메서드 · 상수를 더하기 전에 "이 레이어의 일인가" 를 본다.** 아니면 꺼낸다.
- **도우미 기준** (`helperMethods = {{ws:vars.cleanCode.helperMethods}}`): `few` 면 남겨도 되는 것은 한 곳에서만 쓰고, 짧고(약 10줄), 이 레이어 흐름의 한 단계에 이름을 붙인 것뿐이다. `none` 이면 0개다: 흐름 단계도 협력 객체의 메서드로 꺼낸다. 검사 장치는 `kedovi archrules`.
- **꺼낼 것과 갈 곳:**
  - 업무 규칙 · 계산 · 상태 판단: 그 데이터를 가진 도메인 객체 · 값 객체의 메서드. 여러 객체에 걸치면 `*Policy` · `*Calculator`.
  - 변환 · 파싱 · 형식화: 그 기능의 `*Mapper` · `*Parser` · `*Formatter`.
  - 상수: 값 묶음은 열거형, 환경마다 다르면 설정, 여러 파일이 쓰면 그 개념 이름의 파일 · 클래스.
- **공통화 시점:** 두 번째로 쓰는 곳이 생기면 같은 기능 안으로, 세 번째이거나 다른 기능이 쓰면 공용 위치로. 쓰는 곳이 하나뿐인 유틸 · 미래 대비 추상화는 만들지 않는다 (잘못된 추상화가 중복보다 비싸다).
- **위치 · 이름은 프로젝트 관례가 먼저다.** 같은 종류의 코드가 있는 패키지 · 폴더와 이름 꼴을 찾아 따르고, 새 공용 폴더는 없을 때만 만든다.
- **이름은 하는 일로** (`ShippingFeeCalculator`, `formatPrice`). `Utils` · `Helper` · `Manager` · `Common*` · `misc` 같은 무엇이든 넣는 이름을 새로 만들지 않는다. 범용 함수를 모을 때는 대상 이름을 붙인다 (`DateFormats`).
- 이미 큰 파일이면 도우미를 더 쌓지 말고 이번에 고치는 부분만 꺼낸다. 관계없는 정리는 보고만 한다.
