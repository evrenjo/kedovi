# requirements — 요구사항 정의서 작성

입력: 원천 자료(인터뷰 메모·회의록·현행 문서·현행 소스 경로)와 대상 업무 범위. 없으면 먼저 묻는다.

## 1. 원천 목록
- 읽을 자료를 표로 정리한다: 자료 / 경로 / 종류(인터뷰·문서·소스) / 날짜.
- Word·Excel 원본을 못 읽으면 md 사본을 찾고, 없으면 "원본 미확인" 으로 적는다.

## 2. 요구사항 추출
- 자료에서 "해야 한다 / 필요하다 / 불편하다" 에 해당하는 문장을 모아 한 건씩 쪼갠다. 한 요구사항에 기능 하나.
- 쓰는 곳은 워크스페이스의 사람 문서 원본 `docs-site/` 가 먼저다: 요구 목록은 `docs-site/설계/요구사항.md` (요구 하나에 한 줄), 영역별 동작 · 수용 기준은 `docs-site/기능/` 의 기능 문서(`_template.md` 를 복사, 문서 사이트 탭 이름은 「요구 영역」), 결정은 `docs-site/설계/결정/`.
- `docs-site/` 가 없고 기획 repo(`kind: docs`)만 있으면 그 repo 의 양식을 따른다 (옛 뼈대: `<기획 repo>/20-features/requirements.md` · `<기획 repo>/20-features/_template.md` · `<기획 repo>/01-requirements/_template.md`). 둘 다 없으면 아래 형식.

| 칸 | 내용 |
|---|---|
| ID | `REQ-001` — 기존 번호를 다시 쓰지 않는다 |
| 구분 | 기능 / 비기능(성능·보안·운영) / 데이터 / 인터페이스 |
| 설명 | 누가, 무엇을, 왜 |
| 수용 기준 | 판정할 수 있는 조건 (수치·입력·결과) |
| 출처 | 원천 목록의 자료 이름 (문서 쪽 · 현행 프로그램 이름은 표 아래 `> 출처:` 인용구로) |
| 우선순위 | 필수 / 권장 / 선택 |
| 상태 | 초안 / 검토중 / 확정 |

## 3. 검토
- 중복·충돌 요구사항을 찾아 묶거나 "결정 필요" 로 넘긴다.
- 판정할 수 없는 표현(빠르게·편리하게·충분히)이 남았는지 확인한다.
- 현행 소스에서 나온 요구사항은 현행 프로그램 · 화면 · 배치 이름을 표 아래 인용구(`> 출처: REQ-001 …`)에 단다. 파일명 · 줄 번호는 쓰지 않는다.

## 4. 결과
- 요구사항 목록과 "결정 필요" 목록(질문 / 누가 정하나 / 영향)을 쓴다. `docs-site/` 면 요구는 `docs-site/설계/요구사항.md` 의 행으로, 결정 필요는 `docs-site/설계/결정/README.md` 의 「미결」 표에, 수용 기준은 기능 문서의 `AC-` 행으로 둔다. 상태가 확정이 된 요구는 상태 칸을 `확정` 으로 고친다 (문서 사이트 대시보드의 「확정 요구」 가 센다).
- 기획 repo 만 있으면 그 repo 에 쓴다 (옛 뼈대: 결정 필요는 `<기획 repo>/90-decisions/open-questions.md` 의 `Q-` 행).
- 요약: 건수(구분별) · 결정 필요 건수 · 원본 미확인 자료. 커밋은 사용자가 요청할 때만.
