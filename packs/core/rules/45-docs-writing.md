## 기획 문서 쓰기

문서가 커질수록 고칠 곳이 늘고, AI 가 읽고 맞추는 데 토큰과 시간을 쓴다. 문서는 작게, 사실은 한 곳에 둔다. 그 프로젝트에 이미 정한 문서 관례가 있으면 그것을 먼저 따른다.

- **사실 하나 = 문서 하나.** 정의는 한 곳에만 쓰고, 다른 문서는 ID 링크만 둔다. 동작 · 수용 기준은 기능 문서, 화면 배치는 프로토타입, 수치 · 코드값 · 테이블은 업무 규칙 · 데이터 설계, API 모양은 API 계약, 결정은 결정 기록이 정본이다. 다른 층에 옮겨 적거나 풀어 쓰지 않고, 개수(테이블 수 · 화면 수)는 쓰지 않는다 (도구가 센다). 기능 문서의 「저장」 표는 그 기능이 쓰는 컬럼 · 값 출처 · 조건만 적고 타입 · 설명은 데이터 설계 ID 로 가리킨다 (대조: `kedovi writes check`).
- **코드 · 화면이 문서와 다를 때.** 판정을 먼저 보인다: 정본이 맞음 → 코드를 고칠 일 · 구현이 맞음 → 문서를 고칠 일 · 판단 불가 → 미결 목록. `vars.docs.syncMode` 가 `approve` 면 사용자 승인 뒤 같은 작업에서 정본 한 곳을 고치고 결정 ID 를 단다 (결정이 없으면 `제안` 상태로 새로 만든다). `ask` 면 고치지 않고 미결 목록에 한 줄 + 확인 요청 글.
- **코드의 `@spec` 주석.** 진입점 머리 주석에 한 번 (줄마다 X): 화면 컴포넌트 = 화면 ID + 기능 ID (+ 그 화면 주소 `@route /orders`: `kedovi screens compare` 가 프로토타입과 나란히 찍을 때 쓴다), API 핸들러 = API ID + 기능 ID, 서비스 · 배치 진입 = 기능 ID, 테스트 = 수용 기준 ID (`@spec AC-ORD-003-2`). 대조는 `kedovi docs trace` (`--md` 추적표 · `--new` 새 진입 파일 중 ID 없는 것).
- **바꿀 때는 영향 줄만.** `node packs/core/bin/docs-site.js refs <ID>` 로 그 ID 가 나오는 줄을 찾아 그 줄만 고친다. 문서를 처음부터 다시 읽지 않는다. 정의를 볼 때는 `… show <ID>`.
- **변경 이력은 git 에.** 본문 · 머리말에 이력 표 · 「개정 후보」 절을 쌓지 않는다. 바꾼 이유가 결정이면 결정 기록을 남기고 그 ID 를 건다. 그 프로젝트가 이미 이력 표를 쓰고 있으면 그것을 따른다.
- **제목 · 헤더는 명사 · 명사구.** 문서 제목(`# `, 머리말 `title:`)과 절 헤더 끝에 종결 어미(~다 · ~요 · ~까 · ~나 · ~가 · ~기)나 물음표를 쓰지 않는다. 예: 「설치하기」 → 「설치」, 「무엇이 어디에 저장되나」 → 「저장 위치」.
- **코드 · 줄 번호를 붙이지 않는다.** 문서 사이트는 사람이 읽는다. 소스 코드 · 쿼리 · 설정 파일 원문 · 파일:줄 · 함수 이름을 본문에 옮기지 않고(근거는 아래 인용구로), 표나 mermaid 그림을 먼저 두고 그 아래 짧은 설명으로 맥락을 쓴다. 근거는 기획 ID · 문서 링크로 대고(코드는 repo 가 정본), 코드 표기는 독자가 직접 입력하는 명령 · 설정 키 정도만 쓴다.
- **부가 설명 · 근거 · 출처는 인용구로.** 근거 경로 · 참고 자료 · 측정 수치 · 덧붙임 설명을 본문 문단이나 목록에 줄줄이 쓰지 않고, 그 문단 · 표 아래 인용구(`> 근거: …` · `> 출처: …` · `> 참고: …`)에 모은다. 문서 사이트가 흐린 회색으로 작게 보여 본문을 가리지 않는다. 파일:줄 근거가 꼭 필요하면 이 인용구 안에만 둔다. 이미 본문 괄호에 쓴 파일:줄은 `kedovi docs refs-quote <파일…>` 이 그 아래 인용구로 옮긴다.
- **표 칸은 한두 문장**(약 200자 안). 넘는 설명은 표 아래 「<ID> 자세히」 소절이나 정본 문서로 보내고 칸에는 링크만 둔다.
- **결정은 하나에 한 파일**(`DEC-<번호>`, 상태: 제안 · 확정 · 대체됨). 목록 표는 ID · 결정 한 줄 · 상태만, 대안 · 이유 · 영향받는 문서는 그 파일에. 결정을 뒤집으면 새 결정을 만들고 옛 결정은 `대체됨(DEC-…)`. 그 프로젝트가 주제별 결정 문서를 쓰고 있으면 그것을 따른다 (새 결정은 그 주제의 절에).
- **흐름 · 구성 · 상태 전이는 mermaid.** 순서(→) · 연결 · 상태 바뀜을 ①②③ 문단이나 ASCII 그림으로만 쓰지 않는다 (구성도는 architecture 스킬).
- **개요 문서 순서:** 한 문장 → 범위(포함 · 제외) → 핵심 흐름(그림) → 구성 한눈에(자세히는 시스템 구성 링크) → 이해관계자 · 결정 · 미결 링크.
- **미결은 프로젝트에 목록 하나**(ID · 주제 · 정할 단계 · 출처). 각 문서 끝에는 그 목록의 링크만 둔다.
- **문서 크기.** 한 문서가 `vars.docs.maxKB`(기본 60KB)를 넘으면 주제별로 나눈다. 나눠도 ID 는 바꾸지 않는다.
- **동결.** 구현이 끝나 코드(와 스키마 · 마이그레이션)가 정본이 된 문서는 머리말에 `상태: 동결 (YYYY-MM-DD, 정본: <repo/경로>)` 를 단다. 동결 문서는 고치지 않고, 바뀐 점은 결정 문서에 한 줄 남긴다. 다시 고쳐야 하면 사용자에게 묻고 동결을 푼다.
- **문서 점검 경고**(`kedovi docs build` · `check` 의 「⚠ 문서 점검」: 큰 문서 · 문장형 제목 · 긴 코드 블록 · 파일:줄 참조 · 본문 근거 줄 · 머리말 이력 · 같은 문장 · 긴 표 칸 · 문단형 표 · 칸 안 경위 · 그림 없는 큰 문서 · 메뉴 「기타」)가 나오면 보고에 그대로 옮기고, 이번 작업이 닿은 문서부터 줄인다. 한꺼번에 고치지 않는다.
