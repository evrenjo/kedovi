## 검증 계획과 완료 보고

"그럴듯해 보인다" 는 완료 신호가 아니다. 통과·실패를 돌려주는 검사를 돌리고 그 결과로 말한다.
**테스트를 안 돌렸으면 그 코드는 동작한다고 말할 수 없다.**

### 1. 검증 수단 — 좁은 것부터, 해당하는 것 전부

1. **프로젝트가 정한 명령을 먼저 찾는다** — `README`·`CONTRIBUTING`·`AGENTS.md`·`package.json` scripts·`Makefile`·CI 설정. 표준 명령을 짐작하지 않는다. 프로젝트 래퍼(예: `just test`, `pnpm test`)가 있으면 도구를 직접 부르지 않는다 — 래퍼가 환경·옵션을 맞춘다.
2. **좁게 → 넓게** — 포맷·린트·타입체크 → 바꾼 범위의 테스트 → 공통 모듈·계약·설정을 바꿨으면 더 넓은 테스트 → 빌드 → 실제 실행(화면·API·배치).
3. **버그 수정은 먼저 실패하는 재현**(테스트·명령·화면)을 만들고, 고친 뒤 같은 재현이 통과하는 것을 보인다 (고치기 전 실패 · 고친 뒤 통과). 운영 결함 수정이면 검증표에 「고치기 전 (커밋 · 결과) | 고친 뒤 (커밋 · 결과)」 칸을 두고, 고치기 전 칸이 비면 완료로 보고하지 않는다.
4. **화면·UX 변경은 코드를 읽는 것으로 확인되지 않는다** — 실제로 띄워 전후를 비교한다. 정본(프로토타입 · 화면설계서)이 있는 화면은 정본 요소 체크리스트를 모두 판정하고(`kedovi screens checklist <화면 ID>`) 같은 폭(PC · 폰)으로 나란히 비교한다 (`kedovi screens compare <화면 ID>`, 백엔드 없이 `--mock`). 비교가 미실행이면 완료가 아니다. 비동기 화면·작업은 끝난 뒤에 판정한다 (로딩 중 캡처로 "0건" 오판 금지).
5. **오류는 원인을 고친다** — 검사를 끄거나(`skip`·`ignore`·린트/타입 억제·`--no-verify`) 기대값을 결과에 맞춰 바꾸거나 테스트를 주석 처리해 통과시키지 않는다. 억제가 정말 맞으면(검사기가 틀린 경우) 그 줄에 규칙 이름과 이유를 남기고 보고한다.
6. **"원래 깨져 있던 것" 이라고 단정하지 않는다** — 변경 전 상태(기준 브랜치)에서 같은 명령으로 재현해 본 뒤에만 기존 실패라고 쓴다.

### 2. 출력·시간 관리

- 긴 빌드·테스트 출력은 파일로 받아 두고 필요한 부분만 본다. 코드가 안 바뀌었으면 같은 명령을 다시 돌리지 말고 저장한 출력을 다시 분석한다.
- 전체 스위트처럼 오래 걸리는 검사는 필요성을 판단해 돌리고, 못 돌렸으면 그렇게 적는다.
- 자격 증명·외부 서비스가 필요한 검사는 환경이 갖춰진 경우에만 돌린다. 없는 자격 증명을 가짜 값으로 채우지 않는다.

### 3. 케이스 — 축이 다른 5건 이상

같은 데이터를 반복하지 않는다. 아래 중 **다른 축**으로 고르고, 케이스는 실제 데이터를 조회해서 고른다 ("적당한 것 하나" 로 시작하면 그 하나에 없는 축은 영원히 안 밟힌다).

| 축 | 예 |
|---|---|
| 데이터 출처 | 기존(이관) 데이터 vs 새로 만든 데이터 |
| 규모 | 0건 · 1건 · 다건 |
| 분류값 | 상태·타입·플래그·권한 등급이 갈리는 행 |
| 조건 분기 | 검색·필터 조합, 코드의 if/switch 갈래 |
| 선택 단위 | 단건 · 다건 · 전체 |
| 경계값 | 빈 값 · 최대 길이 초과 · 중복 · 없는 키 · 권한 없음 |

- 자기 변경이 만든 경로만으로 검증하지 않는다 — 같은 커밋이 양쪽을 만든 경로는 반드시 통과한다.
- 분기마다 한 케이스, 무의미한 조합 폭발은 피한다. 중복 케이스·중복 단언을 늘리지 않는다.

### 4. 테스트 코드를 쓸 때

- 새 테스트는 **기존 테스트가 못 잡는 현실적인 회귀**를 잡아야 한다. 이름을 댈 회귀가 없으면 만들지 않는다 (정적 상수·삭제된 로직을 확인하는 테스트 등).
- 테스트가 **실패할 수 있는지** 확인한다 — 구현을 되돌리면 실패해야 한다. 항상 통과하는 테스트는 검증이 아니다.
- 공개 인터페이스로 관찰 가능한 동작을 검증한다. 내부 구현·비공개 함수에 묶지 않는다.
- 기존 테스트 파일·헬퍼·패턴을 먼저 찾아 이어 쓴다. 새 파일은 자연스러운 자리가 없을 때만.
- 시간 대기(`sleep`)로 조건을 기다리지 않는다 — 조건·이벤트를 기다린다. 결정적(같은 입력 → 같은 결과)이어야 한다.
- 스냅샷을 갱신했으면 바뀐 내용을 동작으로 읽고 확인한다. 스냅샷 파일을 손으로 고치지 않는다.

### 5. 완료 보고

- 결론 한 줄 + 검증표 `대상 / 케이스 / 방법 / 기대 / 실제 / 판정`. 못 채운 칸은 "미검증", 안 돌린 검사는 **"미실행 — 구체적 이유"** (막연한 "환경 문제" 가 아니라 이름을 댈 수 있는 실패).
- 주장 대신 증거를 보인다 — 실행한 명령과 결과 요약, 실패 수, 캡처 경로.
- **한 것보다 크게 말하지 않는다** — 계획을 끝낸 일처럼, 작성만 한 패치를 적용한 것처럼, 일부 통과를 전체 통과처럼 쓰지 않는다.
- 버그 수정·리팩터링도 feature 와 같은 검증표를 만든다. 검증표 없는 변경은 완료로 보고하지 않는다.
- 진행 중 가정한 것·범위 밖으로 둔 것을 한 줄씩 적는다.

### 6. 보고 직전 더블체크

- [ ] 바뀐 파일을 **이 대화를 모르는 사람의 눈으로** 다시 읽었는가 (diff 전체)
- [ ] 확인하지 않고 추론으로 넘어간 판정이 있는가
- [ ] 안 본 소비처가 있는가 (읽기·쓰기·배치·내보내기·복사 경로, 대칭 기능)
- [ ] 주석·문서에 지운 이름이나 옛 동작이 남았는가
- [ ] 실행하지 않은 검사가 있는가 (빌드·타입체크·테스트·화면·쿼리)
- [ ] 내 변경 때문에 안 쓰이게 된 import·변수·함수를 지웠는가 (기존 죽은 코드는 지우지 말고 알린다)
- [ ] 사용자 결정 대기 항목을 임의로 진행하지 않았는가
- [ ] 임시 파일·띄운 프로세스를 정리했는가
