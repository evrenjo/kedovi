# team: 역할 에이전트로 팀 구성

## 실행 방식 선택

세션 시작 줄의 「🧩 역할 에이전트 실행 방식」 판정을 따른다 (훅 `hooks/team-mode.js` 가 환경으로 정한다. 이어서 시작 · 대화 요약 뒤에도 다시 나온다). 팀 모드인데 역할 에이전트를 이름 없이 띄우면 훅이 막는다 (대화가 요약된 뒤에도 같다). **작업을 시작할 때 사용자에게 한 줄로 알린다**: "팀 모드(tmux 창)로 진행" 또는 "서브에이전트로 진행 · 사유: tmux 세션 밖".

| 방식 | 띄우는 법 | 결과 받기 | 끝내기 |
|---|---|---|---|
| 팀 모드 (Claude Code agent teams) | 역할마다 `Agent` 도구에 `name`(역할 이름)을 주어 팀원으로. 팀원은 이 대화를 모르므로 지시서를 완결되게 (「넘겨주기」) | `SendMessage` 로 받거나, `TaskCreate` 로 나눠 준 일의 완료를 `TaskList` 로 본다 | 보고 전에 일하는 중인 팀원이 0 이게. 리뷰 뒤 수정이 남은 팀원은 대기로 두고, 수정까지 끝나면 종료 지시 (대기로 오래 남으면 훅이 알린다) |
| 서브에이전트 | 역할 이름으로 `Agent` 도구 | 결론만 돌아온다 | 결과를 받으면 끝 |

- 팀 모드 조건: 팀 기능이 켜져 있고(`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`), `teammateMode` 가 `tmux` 면 tmux 가 설치돼 있을 때 (세션 밖이면 Claude Code 가 tmux 세션을 만들고 입력창 오른쪽에 이름을 보여 준다. 사용자는 다른 터미널에서 `tmux attach -t <이름>` 으로 본다). `in-process` 면 tmux 없이 같은 터미널 안에서 팀 모드.
- 상한(개인 지침의 「역할 에이전트 상한」) · 역할 모델 · 파일 소유 · 보고 형식은 두 방식에 똑같이 적용된다. 팀원 생성도 `Agent` 도구라 같은 훅이 센다.
- **팀원 승인 질문**: 팀원 창에 권한 승인(예 · 아니오)이 뜨면 팀원은 멈추고, 그 질문은 리더 화면에 보이지 않는다. 팀원을 띄울 때 사용자에게 「팀원 창에 승인 질문이 뜨면 그 창에서 승인해야 시작합니다」 를 알린다. 훅이 승인 대기를 적어 두고 리더의 다음 요청 · 턴 끝에 알리며(텔레그램을 켰으면 바로), 그러면 사용자에게 그 창에서 승인하라고 알린다. 읽기 · 조회 명령(git log · grep · `kedovi docs show` 등)은 프로젝트 설정에 미리 허용돼 있다. 같은 조회 명령이 계속 묻으면 `workspace.json` 의 `claude.settings.permissions.allow` 에 넣자고 제안한다.
- **첫 응답 확인**: 팀원을 띄운 뒤 첫 보고(SendMessage)나 할 일 진행(TaskList)이 오지 않은 채 다음 요청을 받으면, 진행을 기다리지 말고 사용자에게 그 팀원 창을 확인해 달라고 먼저 알린다.

> Codex: 팀 모드가 없다. 아래 하위 에이전트(`spawn_agent`) 방식으로 한다.

## 쓸지 말지

- **쓴다**: 여러 repo·계층(데이터·서버·화면)에 걸치거나, 조사·구현·검증이 서로 독립으로 나뉠 때. 많이 읽어야 하는 조사는 결론만 받으려고 맡긴다.
- **안 쓴다**: 한 파일·한 계층의 작은 수정, 순서가 강하게 묶인 작업. 조율 비용이 더 크다.
- **개수**: 이 PC 의 상한(개인 지침의 「역할 에이전트 상한」) 안에서 가장 적게. 역할을 줄이고, 같은 역할은 앞 에이전트에게 이어서 맡긴다.

## 역할

역할 목록은 개인 지침(`CLAUDE.local.md` · `AGENTS.override.md`)의 **「팀 구성」 표**가 정본이다. 쓰는 팩의 역할 전부(core 일반 역할 · 계층 팩 · `packs/project/agents/` 의 프로젝트 역할)가 등급 · 권한 · 기본 모델과 함께 들어 있다. 정의 파일은 `packs/<팩>/agents/<이름>.md`. 스키마 · 마이그레이션 · SQL 이 끼면 `dba`, 컨테이너 · 배포 · IaC 가 끼면 `infra` 를 맡긴다 (표에 있을 때. DB · 인프라 스택이 있는 repo 면 붙는다).

- 설계서·기능정의서·대응표처럼 **결정을 빠짐없이 옮겨야 하는 문서**는 `spec-writer`, README·사용법 갱신은 `documenter`.
- 필요한 역할이 목록에 없으면 가장 가까운 역할로 띄우고 지시서 첫머리에 **임시 역할**(목적 · 소유 파일 · 하지 않을 것)을 적는다. 같은 임시 역할이 반복되면 `packs/project/agents/` 에 역할로 만들지 사용자에게 제안한다.

**리더**(지금 대화하는 에이전트)는 분해·파일 소유 배정·계약 확정·통합 점검·사용자 보고를 맡고, 직접 편집은 최소로 한다.

## 팀 구성: 역할마다 모델 고르기

개인 지침 「팀 구성」 의 **모드**를 본다. 고정이면 역할 기본 모델을 그대로 쓰고 6번(구성표)만 한다. 자동이면 아래 순서로 고른다.

1. **작업 유형**: 코딩 · 에이전트 코딩(여러 파일 · 도구 사용) · 추론(원인 분석 · 설계 판단) · 데이터 분석 · 문서.
2. **역할**: 아래 「작업 유형별 구성」 에서 출발해 작업에 맞게 더하거나 뺀다. 상한(「역할 에이전트 상한」) 안에서 가장 적게.
3. **등급**: 역할의 등급에서 출발해 이번 일에 맞게 정한다.
   - high: 계약 · 스키마 · 보안 · 데이터처럼 되돌리기 어려운 변경, 원인 분석, 영역·단계 끝 감사 리뷰
   - standard: 범위가 정해진 구현 · 테스트 작성 · 일상 리뷰
   - low: 반복 실행 · 정리 · README 갱신 · 단순 조사
4. **모델**: 「쓸 수 있는 모델」 메뉴 안에서만 고른다.
   - 기본은 그 등급의 모델(등급 칸, 지금 성향 기준)이다.
   - 작업 유형 점수가 뚜렷이 높은 모델이 같은 값대에 있으면 바꾼다.
   - **선호** 가 있는 역할은 선호 모델을 쓴다.
   - **요금제 여유도**(「팀 구성」 의 요금제 줄 · 메뉴의 회사 칸): 빠듯한 회사 모델은 선호 역할과 다른 회사로 대신할 수 없는 high 작업에만, 그 회사 최상위 모델은 기본으로 쓰지 않는다. 넉넉한 회사에 high 작업을 먼저 준다. 종량은 같은 품질이면 싼 모델. 요금제를 모르면 등급대로.
   - 리뷰는 두 회사를 다 쓸 수 있으면 구현과 다른 회사 모델로.
   - 사용자가 대화로 옵션을 말하면("품질 우선" · "리뷰는 Claude 로") 그 세션 동안 따른다. 계속 쓰려면 `kedovi team-mode` · `kedovi ai` 를 알려 준다.
5. **근거가 없을 때만 웹 검색**: 메뉴에 없는 모델(게이트웨이 전용 · 새 모델)을 써야 할 때, 카탈로그 확인일이 45일 넘었을 때, 사용자가 "최신으로 찾아보고 골라" 라고 했을 때.
   - 먼저 `handoffs/MODELS.md` 를 본다. 같은 모델을 30일 안에 조사한 줄이 있으면 그것을 쓴다.
   - 공식 문서와 독립 측정(LiveBench 등)을 우선한다. 홍보 글 · 날짜 없는 비교 글은 근거로 쓰지 않는다.
   - 찾은 결과는 `handoffs/MODELS.md` 표에 한 줄 더한다: `| 모델 | 회사 | 확인일 | 작업 유형별 강점 | 출처 |`. 팀이 같이 쓰는 파일이라 다음 사람은 다시 찾지 않는다. 다음 핸드오프 커밋에 함께 넣는다.
6. **구성표를 알리고 바로 시작**한다. 다만 웹 검색으로 고른 모델이 있거나, high 가 4개 이상이면 승인을 받고 시작한다.

```
팀 구성 (자동 · 표준 · Claude Max 5x 넉넉 · GPT Plus 빠듯)
| 역할 | 모델 | 이유 |
| 분석 | sonnet · high | 현행 코드 조사, 코딩 점수 상위 |
| 구현 api | opus · high | 계약 변경 포함 (high) |
| 리뷰 | gpt-6.1-sol · medium | 다른 회사 모델 (선호) |
근거: 카탈로그 2026-10-01 · LiveBench 2026-06-25
```

호출: Claude Code 하위 에이전트는 역할 이름 + 모델(별칭)을 준다. 추론 강도까지 바꾸려면, 또 상대 회사 모델이면 `delegate.js start --to <도구> --model <m> --effort <강도>`. 메뉴의 「부르는 법」 칸을 따른다.

### 상대 회사 모델이 맡는 역할

AI 게이트웨이를 쓰는 Claude Code 에서는 GPT 역할도 **보통 하위 에이전트**다 (역할 파일의 모델이 게이트웨이 모델). 아래 위임은 각 회사 서비스에 직접 연결했을 때다.

역할 에이전트의 설명에 "(OpenAI Codex … 에게 위임)" · "(Claude … 에게 위임)" 이 붙어 있으면 그 역할은 **상대 도구가 한다** (`packs/core/bin/delegate.js`). 평소처럼 그 이름으로 맡기되:

- **지시서를 완결되게** 쓴다. 위임받은 쪽은 이 대화를 모른다. 목적 · 앞 역할의 결론과 근거(`파일:라인`) · 소유 파일 · 계약 · 검증 명령 · 멈출 조건을 빠짐없이.
- 쓰기 역할은 소유 파일을 반드시 준다. 같은 파일을 다른 역할과 동시에 맡기지 않는다.
- 별도 프로세스라 느리다. **시작할 때 사용자에게 진행 보기 명령을 한 줄로 알린다**: `kedovi delegate watch <작업 id>` (다른 터미널에서 상대 에이전트가 읽고 실행하는 것이 줄마다 보인다). 기다리는 동안 `wait` 가 시간 안에 안 끝나면 진행 현황(경과 · 읽은 파일 · 명령 · 최근 동작 · 최근 말)이 나오니, 다시 기다리기 전에 그 요약을 사용자에게 한두 줄로 전한다.
- 결과의 "이번에 바뀐 파일" 을 보고 소유 밖 변경이 있으면 되돌리게 한다.
- 위임받은 쪽은 커밋·push 하지 않는다. 상대 도구가 없는 PC 에서는 같은 도구 모델로 바뀌어 있다 (sync 가 알린다).
- 리뷰 위임은 `--scope <범위 라벨>` 을 준다 (같은 기능이면 같은 라벨). 차수를 세어 앞 차수 블로커를 지시서에 붙이고, 같은 영역이 다시 블로커면 `[반복]` 으로 표시된다. 3차부터는 시작 때 경고가 나온다: 땜질을 멈추고 원인 구조를 정리했는지, 남은 지적을 한계로 문서화할지 사용자에게 묻는다.
- 결과 머리의 ⚠ 를 먼저 본다: 실패 원인(사용량 한도 · 로그인 · 시간 초과)과 대안, 실행 중 대상이 바뀌어 결과가 낡았을 수 있음. 사용량 한도면 「상대 도구로 다시:」 명령을 그대로 실행한다.
- 읽기 전용 Claude 리뷰어는 읽기용 셸(`git diff` · `git show` · `git log` · `grep`)을 직접 돌린다. diff 를 파일로 떠서 넘기지 않아도 된다.

> 하위 에이전트를 지원하는 도구면 위 이름으로 역할 에이전트에게 맡긴다.
> Codex: 역할 파일이 하위 에이전트에 적용되지 않는다. 위에서 고른 모델(고정이면 개인 지침 「팀 구성」 표의 기본 모델)과 추론 강도를 `spawn_agent` 에 넣고, 지시 첫 줄에 그 역할 정의 파일을 읽고 따르라고 적는다.
> 지원하지 않으면 리더가 해당 `packs/<팩>/agents/<이름>.md` 를 읽고 그 역할을 **차례로** 수행한다 (역할이 바뀔 때마다 그 파일의 「하지 않는다」 를 지킨다).

## 작업 유형별 구성

| 유형 | 순서 (→ 는 앞 결과를 넘긴다, ∥ 는 병렬) |
|---|---|
| 버그 수정 | analyst(원인·영향) → tester(실패 재현) → implementer → tester(재현 통과 + 회귀 5건) → reviewer |
| 기능 추가 | analyst → architect → implementer ∥ implementer (계층별) → tester ∥ reviewer → documenter |
| 리팩터링 | analyst(소비처 전수) → architect(단계 분할) → implementer → tester(전후 동작 동일) → reviewer |
| 레거시·현행 분석 | analyst ∥ analyst (영역별) → architect(대응 방안, 필요할 때만) → spec-writer(분석 문서) |
| 설계·기능정의 문서 | analyst(원본 결정·근거 모으기) → spec-writer(결정 전수 옮기기 + `check-docs --cover`) → reviewer(원본과 대조) |
| 리뷰 | reviewer ∥ reviewer (관점별: 정확성·보안 / 계약·테스트). 다른 벤더 의견이 필요하면 `cross-review` 스킬 |
| 여러 repo 작업 | 리더가 계획과 repo 간 계약(API · 이벤트 필드)을 먼저 확정 → repo 별 implementer 1~2명 동시 → reviewer(관련 변경 묶음 단위, repo 를 넘는 계약은 한 묶음) → 리더가 통합 검증(계약 양쪽을 함께 돌린다) |

작은 작업이면 역할을 줄인다. 분석 결과가 이미 있거나 계획이 요청에 정해져 있으면 그 단계를 건너뛴다.

한 repo 안에서 나눌 때는 파일 하나 단위가 아니라 **백엔드 · 프론트 · 도메인 단위**로 나눈다. 여러 repo 작업이 상한(「역할 에이전트 상한」)보다 많은 repo 에 걸치면 번갈아 처리하지 말고, 올릴 값(repo 수 기준)과 설정 위치(`workspace.json` 의 `agents.limits`)를 보이고 사용자에게 묻는다.

## 파일 소유: 충돌 막기

- 쓰기 역할마다 **소유 파일(또는 폴더) 목록**을 준다. 같은 파일을 두 에이전트가 동시에 고치지 않는다.
- 경계 파일(공유 타입·스키마·API 계약)은 한 명이 먼저 만들고 알린 뒤 나머지가 시작한다.
- tester 는 테스트 파일만, documenter · spec-writer 는 문서 파일만 소유한다. 제품 코드 결함은 해당 implementer 에게 되돌린다.
- 소유 밖 변경이 필요하면 멈추고 리더에게 알린다. 리더가 소유를 다시 나눈다.

## 넘겨주기

각 역할의 보고 형식(각 정의 파일의 「보고 형식」)이 다음 역할의 입력이다. 리더는 넘길 때 아래를 붙인다.

- 목적 한 줄, 앞 역할의 결론·근거(`파일:라인`), 소유 파일, 계약, 멈출 조건.
- `AGENTS.md` 의 「repo 별 작업 규칙」 해당 줄. 각 역할이 시작 전에 읽는다.
- 앞 역할의 **추정·미확인** 항목은 그대로 표시해 넘긴다. 다음 역할이 확인됨으로 바꿔 쓰지 않게.

## 모든 역할 공통 지시 (리더가 지시문에 넣는다)

- 커밋·푸시·PR·DB 반영·외부 전송·파괴적 명령은 하지 않는다. 사용자 승인을 받아 리더가 한다.
- 테스트·화면 실행은 검증 계획이 승인된 뒤에.
- 범위 밖 발견은 리더에게 한 줄로만, 손대지 않는다.
- 보고는 한 번. 같은 내용을 다시 보내지 않는다 (메시지로 보냈으면 대기 알림에 되풀이하지 않는다).
- git 은 맡은 repo 에서 `git -C <repo 경로>` 로 부른다. 워크스페이스 루트의 git 쓰기와 push 는 훅이 막는다.

## 흐름

1. **합의된 작업 안에서** 리더가 유형을 정하고 역할·순서·파일 소유를 정해 **한두 줄로 알리고 바로 시작**한다. 일을 나누는 방법은 묻지 않는다. 상한을 넘겨야 하거나, 설계 선택지가 결과를 크게 가르면 그때만 사용자에게 묻는다.
   단계를 넘어가거나(분석 → 기획 등) 그 단계의 진행 방식(논의할 항목·순서·산출물 형태)이 아직 정해지지 않았으면 팀을 띄우기 전에 사용자와 정한다 (상시 룰 「커뮤니케이션」).
2. 역할을 순서대로(병렬 가능한 것은 함께) 띄우고 결과를 받아 다음 역할에 넘긴다.
3. **검증 순서: 구현 → 해당 검사 → 리뷰 → 수정 → 해당 검사.** 리뷰를 맡기기 전에 그 변경에 해당하는 검사(빌드 · 테스트 · 회귀 검사)를 통과시키고 지시서에 `검사: <명령> 통과` 줄을 넣는다 (검사가 없는 변경은 `검사: 없음 (사유)`). 프로토타입이 있는 화면을 바꿨으면 지시서에 `| 프로토타입 요소 | 구현 | 다른 이유 |` 비교표와 스크린샷 경로(`kedovi screens compare <화면 ID>`)를 넣는다. 없으면 훅이 리뷰 위임 · 리뷰 에이전트를 막는다 (`kedovi team-mode enforce check`). 긴 검사는 리뷰 차수마다 낡은 코드로 돌리지 않는다.
   tester·reviewer 가 낸 결함은 해당 implementer 에게 되돌려 고친 뒤 **같은 검증을 다시** 돌린다.
   리뷰 확인을 켠 워크스페이스(`kedovi review status`)는 리뷰 없이 commit · push 하면 훅이 리뷰 안 된 줄 수를 알리거나 막는다. 코드뿐 아니라 문서도 같다. 리뷰를 생략하려면 사용자에게 먼저 묻고, 승인받으면 `kedovi review skip --reason "<사유>"`.
4. 리더가 통합 점검: 여러 역할의 결론이 서로 맞는지, 추정이 확인됨으로 둔갑하지 않았는지 본다. 어긋나면 근거를 대조해 판정하고, 판정이 안 되면 사용자에게 묻는다.
5. 사용자 보고: 결론 한 줄 · 변경 요약 · 영향 범위 · 검증표(`.agents/rules/core--21-verification.md`) · 남은 결정.
6. **정리**: 보고 시점에 **일하는 중인** 에이전트·위임 작업이 0 이어야 한다. 기다리는 동안 다른 일을 하려면 위임 `wait` 를 백그라운드로 돌리고 답변 끝에 상태 줄(아래)을 적는다 (상태 줄 없이 멈추면 훅이 알린다).
   팀원 알림이 리더의 마지막 지시보다 먼저 쓰인 보고면(지시 전 상태) 사용자에게 길게 다시 설명하지 않고 「앞 지시 기준 보고」 한 줄로 넘긴다.
   일을 마치고 대기(idle) 중인 에이전트는 "돌고 있음" 에 들지 않는다. 순서는 구현 → 리뷰 → 지적 수정(같은 에이전트에게 이어서) → 다시 검증 → **그다음 종료**. 수정 요청이 남았는데 미리 종료하면 다시 부를 수 없어 새로 띄우고 맥락을 다시 넘겨야 한다.
   사용자가 리뷰 결과를 보고 고칠지 정해야 하면 그 에이전트를 대기로 두고 보고에 "대기 중: <역할>" 을 적는다. 다음 요청에서 고칠 일이 없으면 종료한다.
   > Claude Code 팀 모드: 종료는 팀원마다 **정식 종료 요청**(`SendMessage` 의 `shutdown_request`)을 보내고 그 팀원의 승인(종료) 알림을 받은 뒤에 끝난 것이다. 일반 메시지("종료해 주세요")로는 끝나지 않는다.
   > tmux 창 · 프로세스를 직접 닫지 않는다 (훅이 막는다). 승인 전에 닫으면 등록만 남아 대기(○) 팀원이 쌓이고, 다시 요청하면 기록에서 되살아난다. 종료 요청은 팀원이 하던 요청을 끝내야 처리되고 거부될 수도 있다. 요청 뒤 팀원 목록을 확인하고, 몇 분 지나도 남아 있으면 `TaskStop`(`task_id` 에 팀원 이름)으로 멈춘다 (등록까지 빠진다). 그래도 남으면 사용자에게 남은 팀원 이름을 알린다.
   기다리며 턴을 끝낼 때(팀원이 남았거나 백그라운드 작업 · 위임이 도는 중)는 답변 끝에 상태 줄을 적는다: `지금 도는 것: <무엇, 없으면 없음> · 예상 종료: <언제쯤, 모르면 모름> · 사용자가 할 일: <있음(무엇) | 없음>`. 화면의 팀원 목록은 대기 중인 팀원도 시간이 계속 올라가 사용자가 일하는 중으로 안다. 다시 맡길 일이 정해져 있지 않은 팀원은 남겨 두지 않고 종료한다.
   > Claude Code: 상태 줄이 없으면 멈출 때 훅이 한 번 막는다 (`kedovi team-mode enforce status`). 끝남 알림(텔레그램)에도 일하는 팀원 · 대기 팀원 · 백그라운드 작업 수가 한 줄 붙는다.
   > 일하는 팀원 · 위임 작업이 60분을 넘으면 멈출 때 훅이 한 번 막는다. 지금까지 한 것 · 남은 것을 한 줄씩 보이고 계속할지 · 범위를 줄일지 · 멈출지 사용자에게 묻는다 (`kedovi team-mode enforce run`, 상한은 팀 값).
   > 일을 마치고 대기로 10분 넘게 남은 팀원이 있으면 멈출 때 훅이 한 번 막고 이름과 대기 시간을 알린다 (같은 팀원은 30분 뒤 다시). 종료하거나, 남겨 둘 것이면 보고에 "대기 중: <역할> · 사유" 를 적는다. 수준 · 시간은 `kedovi team-mode enforce idle`.
   > 팀원 상태는 팀원의 메시지 · 작업 목록으로 본다. `tmux capture-pane` 과 `sleep` 으로 화면을 엿보며 기다리지 않는다.
