# interview: 의도 인터뷰

사용자가 요청을 완벽하게 정리해 오기를 기대하지 않는다. **무엇(What)만 있고 왜(Why)가 빠진 요청은 추측으로 채우지 않고, 질문으로 끌어낸다.**

## 1. 쓸 때 · 쓰지 않을 때

| 구분 | 경우 |
|---|---|
| 쓴다 | 새 기능 · 동작 변경 요청에서 아래 네 칸 가운데 하나라도 요청 · 기록(기능 문서 · 작업 기록 · 로드맵 · 결정 기록)으로 채워지지 않을 때. 사용자가 「인터뷰해 줘」 라고 할 때 |
| 쓰지 않는다 | 오타 · 한두 줄 수정, 단순 질문 · 조회, 네 칸을 이미 말한 요청, 이미 의도 문서가 있는 작업 |

코드 · 문서로 확인되는 것은 묻지 않고 직접 확인한다. 묻는 것은 **사용자만 정할 수 있는 것**뿐이다.

## 2. 네 칸

| 칸 | 끌어낼 것 |
|---|---|
| 목적(왜) | 누가 무엇을 할 수 있게 되나. 지금 무엇이 불편하거나 막혀 있나 |
| 성공 기준 | 끝났다고 볼 확인 방법 (화면 · 명령 · 숫자 · 사람의 확인) |
| 범위 | 이번에 할 것 · 하지 않을 것 |
| 제약 | 지켜야 할 것 (기존 동작 · 데이터 · 일정 · 기술 · 보안) |

## 3. 진행

1. 첫 줄에 「만들기 전에 의도를 n가지 묻습니다」 를 알리고 바로 첫 질문을 한다.
2. **한 번에 하나씩** 선택지 질문으로 묻는다 (보기 2~4개, 권장안 첫째와 이유 한 줄, 제목 끝에 `주제 n/N`). 보기는 코드 · 기록을 읽고 만든 구체적인 안이다. 빈 질문(「목적이 무엇인가요?」)만 던지지 않는다. 앞 답에 따라 다음 질문을 바꾼다.
3. 답이 「모름 · 알아서」 면 권장안으로 적고 「가정」 으로 표시한다.
4. **엇갈리는 보기로 확인한다.** 다 모이면 의도를 3~5줄로 요약해 보인다. 이어서 그 의도로 판단이 갈리는 구체적인 상황 하나를 골라 「이 경우 어떻게 되어야 하나」 를 선택지로 묻는다. 보기 하나는 요약을 그대로 따른 결과, 다른 하나는 그럴듯한 다른 해석의 결과로 만든다. 고른 답이 요약과 다르면 요약을 고치고 한 번 더 확인한다.
5. 의도 문서를 저장한다 (아래 4절).
6. **구현은 새 맥락에서 시작한다.** 인터뷰한 대화에는 버린 안 · 추측이 섞여 있다.
   - 팀 모드면 의도 문서를 지시서로 작업 리더에게 넘긴다.
   - 혼자 작업이면 의도 문서 경로를 알리고 새 대화에서 그 문서로 시작하기를 권한다. 사용자가 이어서 하자고 하면 이 대화에서 `go` 스킬 3단계로 간다.

## 4. 의도 문서

- 위치: `ai-docs/의도/<YYYY-MM-DD>-<짧은 이름>.md`. ai-docs 규칙을 따른다 (첫 줄 머리: 한 줄 요약 · 날짜 · 관련 ID, `ai-docs/README.md` 폴더 목록에 「의도」 줄이 없으면 더한다).
- 내용: 네 칸 · 확인 질문과 고른 답 · 가정 · 남은 질문.
- 기능 문서(`docs-site/기능/`)가 있으면 그 명세 절의 목표 · 완료 기준도 같은 내용으로 고친다 (사람이 읽는 글 형식).
- `착수 전 확인:` 의 목적 · 성공 기준 칸은 이 문서에서 옮긴다.
