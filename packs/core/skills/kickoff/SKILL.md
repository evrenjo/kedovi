# kickoff: 방향 인터뷰

`kedovi init` 은 프로젝트명 · repo 만 받는다. 유형 · 분야 · 진행 방식 · 무엇을 만들지는 **이 인터뷰가 정한다** (`workspace.json` 의 `project.onboarded` 가 `false` 인 동안). 끝나면 `kedovi kickoff done`.

## 0. 시작

첫 답변에 한 줄로 알리고 바로 주제 1 의 첫 질문을 한다:
「방향 인터뷰(7개 주제)를 한 번에 하나씩 묻고, 끝나면 개요 · 설계 · 기능 문서 초안을 만듭니다. 나중에 하려면 말해 주세요.」

- 사용자가 미루면 미루고 요청을 처리한다. 다시 시작은 「방향 인터뷰」 라고 말하면 된다고 한 줄 알린다.
- 이미 기획 문서가 있으면(주제 4) 그 문서에서 답을 뽑아 확인만 받는다. 새로 묻지 않는다.

## 1. 묻는 순서 (주제 n/N)

**한 번에 한 질문**만 하고, 질문 앞에 `주제 n/7 · <주제 이름>` 을 붙인다 (예: 「주제 1/7 · 무엇 · 누가」, 대시(—)는 쓰지 않는다). 답을 한두 줄로 되짚어 확인한 뒤 다음으로 간다. 고르는 질문은 선택지로(권장안 첫째). 모르는 것은 지어내지 않고 `미정` 으로 둔다.

| 주제 | 묻는 것 | 끝나는 조건 · 바로 하는 일 |
|---|---|---|
| 1/7 무엇 · 누가 | 무엇을 만드나 (한 문장) · 누가 쓰고 그 사람의 문제는 무엇인가 | 한 문장 + 사용자 유형 1~3개 |
| 2/7 유형 | 새로 만든다 · 운영 중인 서비스를 고친다 · 옛 시스템을 옮긴다(이전) · 구축 전 분석만 | 아래 「유형 대응」 의 명령을 실행 (팀장) |
| 3/7 분야 | 웹 · 앱 · 게임 · 웨어러블 · 장치 · IoT · 임베디드 (주제 1 의 답으로 짐작한 것을 권장안으로) | 아래 「분야 대응」 의 명령을 실행 (팀장) |
| 4/7 기존 자료 | 기획서 · 화면 · 옛 소스 · 회의록이 어디 있나 (repo · 폴더 · 주소) | 위치 목록. repo 면 `kedovi repo add <주소> --kind legacy` 또는 `--kind docs` 를 제안 |
| 5/7 첫 기능 · 마일스톤 | 처음 만들 기능 목록 (기능마다 한 줄) · 마일스톤(이름 · 목표 날짜. 기본 이름은 분야대로: 아래 표) · 기능을 어느 마일스톤에 넣나 | 기능 표 (번호 · 이름 · 마일스톤) |
| 6/7 개발 표준 · 스택 | 언어 · 프레임워크 · DB · 배포 환경 · 코드 관례 · 테스트 기준 (게임은 엔진 판 · 성능 예산, 장치 · IoT 는 MCU · SDK 판 · 메모리 · 전력 예산 · MISRA 같은 코딩 규칙). 화면이 있으면 화면 품질 수준도: 공공 사업(KRDS · KWCAG 2.2 · 품질관리 지침) · 일반 서비스(WCAG 2.2 AA) · 사내 도구 | 표준 표. 이미 코드 repo 가 있으면 감지된 스택(`kedovi detect`)을 보여 주고 확인만. 화면 품질 수준은 `kedovi screens quality-level public\|standard\|light` |
| 7/7 규칙 | 킷이 넣은 규칙 중 팀에 맞지 않는 것 | `kedovi rules list` 를 보여 주고, 끌 것은 `kedovi rules off <ID…>` |

### 유형 대응 (주제 2)

| 답 | 명령 |
|---|---|
| 새로 만든다 | 그대로 (`new` · 기능 단위). 바꿀 것 없음 |
| 운영 중인 서비스를 고친다 | `kedovi type enhancement --approach feature` (이슈마다 운영 반영이 주된 일이면 `--approach issue`) |
| 옛 시스템을 옮긴다 | `kedovi type modernization --approach feature` (옛 소스는 주제 4 에서 참고 자료 repo 로) |
| 구축 전 분석만 | `kedovi type consulting` |

### 분야 대응 (주제 3)

| 답 | 명령 | 마일스톤 기본 이름 |
|---|---|---|
| 웹 · 앱 | 그대로 (`web`). 바꿀 것 없음 | 1차 오픈 · 2차 |
| 게임 | `kedovi domain game` | 프로토타입 · 버티컬 슬라이스 · 알파 · 베타 · 골드 · 라이브 |
| 웨어러블 · 장치 | `kedovi domain device` | POC · EVT · DVT · PVT · 양산 |
| IoT · 임베디드 | `kedovi domain iot` | POC · EVT · DVT · PVT · 출시 |

분야를 고르면 분야 규칙 팩이 켜지고, `docs-site/` 에 그 분야의 빈 쪽(설계 · 테스트)과 분야용 기능 문서 틀이 생긴다 (고친 파일은 건드리지 않는다). 기능 문서는 그 틀(`docs-site/기능/_template.md`)을 따른다.

진행 방식은 기본이 기능 단위(`feature`: 설계 기준을 먼저 정하고 기능마다 명세 → 설계 → AI 구현 → 검증 → 배포)다. 사용자가 다른 방식을 원할 때만 `kedovi approach sprint|full|issue`.

## 2. 남기는 것 (사용자가 확인한 뒤)

워크스페이스의 `docs-site/` 에 쓴다 (사람이 읽는 문서 원본). 같은 사실을 두 곳에 쓰지 않는다. 기존 기획 repo 를 연결했으면 그 repo 의 구조를 따르고, 새 구조로 옮기기는 나중에 따로 한다.

| 파일 | 내용 |
|---|---|
| `docs-site/개요.md` | 한 문장 · 사용자와 문제 · 범위(하지 않을 것 포함) · 마일스톤 표 · 기존 자료 위치 |
| `docs-site/설계/요구사항.md` | 기능 목록 표(번호 · 이름 · 마일스톤 · 한 줄 설명) · 아직 정하지 않은 것 |
| `docs-site/설계/아키텍처.md` | 구성 요소(화면 · 서버 · DB · 외부 연동) 초안. 자세한 구성도는 `architecture` 스킬로 나중에 |
| `docs-site/설계/개발표준.md` | 주제 5 의 표준 표 |
| `docs-site/기능/NNN-이름.md` | 기능마다 한 파일 (`001-회원관리.md`). 아래 머리 + 명세 · 설계 · 검증 절(지금은 명세 몇 줄만) |

기능 파일 머리 (제목 바로 아래 한 줄. 문서 사이트가 이 줄을 읽는다):

```markdown
# 001 회원관리

> 번호: 001 · 이름: 회원관리 · 마일스톤: 1차 오픈 · 단계: 명세
```

- 장치 · IoT 는 대상 보드 판을 덧붙인다: `· 보드: HW-001`.

- 단계 값은 `명세 · 설계 · 구현 · 검증 · 배포` 중 하나. 처음엔 모두 `명세`.
- 작업 목록(할 일)은 문서에 쓰지 않는다. 할 일은 로드맵(`handoffs/PLAN.md`)과 작업 항목에 둔다.

## 3. 마무리

1. 문서 사이트를 다시 만든다: `kedovi docs build` (사이트가 아직 없거나 명령이 실패하면 한 줄 알리고 넘어간다).
2. 로드맵 「설계 기준」 의 체크 목록에서 끝낸 것을 `[x]` 로 고친다.
3. `kedovi kickoff done` 을 실행한다 (팀장. `project.onboarded` 를 `true` 로).
4. 바뀐 파일을 보여 주고 커밋할지 묻는다 (`docs: 방향 인터뷰 결과`). 원격이 없으면 팀과 나누는 법 한 줄: `kedovi remote add <주소>`.
