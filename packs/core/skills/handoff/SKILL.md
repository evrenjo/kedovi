# handoff: 작업 마무리

본인 작업을 다음 세션(나 또는 다른 사람)이 바로 이어받을 수 있게 기록한다. **본인 폴더만** 읽고 쓴다. 다른 개발자의 `handoffs/{타인}/` 은 건드리지 않는다. 예외는 팀 공용 로드맵 `handoffs/PLAN.md` 의 상태 갱신(5.5)뿐이다.

기록은 **작업별로** 남긴다. 날짜순 주간 기록에 자세한 내용을 쌓으면 금방 수십만 자가 되어 다음 세션이 필요한 부분을 찾지 못한다.

| 파일 | 무엇 | 크기 |
|---|---|---|
| `handoffs/{id}/topics/<작업>.md` | 한 작업의 결정 · 원인 · 상태 · 검증 · 남은 일(완료 조건). **자세한 내용과 미완 업무의 정본은 여기** | 작업마다 |
| `handoffs/{id}/YYYY-Www.md` | 날짜마다 작업별 한두 줄 + 작업별 기록 링크 | 하루 3KB 이내 |
| `handoffs/{id}/LATEST.md` | 지금 상태 스냅샷 (재개가 먼저 읽는다) | 4KB 이내 |
| `handoffs/{id}/TODO.md` | 사용자가 등록한 할 일. **사용자가 넣어 달라고 할 때만** 쓴다 | 30개 이내 |
| `handoffs/{id}/INDEX.md` | 작업 색인 (도구가 만든다) | |

## 0. 준비

```bash
git config user.name                                             # {id} (워크스페이스 루트에서)
node -e "const w=require('./packs/core/lib/workspace');console.log(w.localDate(), w.isoWeek())"   # 오늘, ISO 주차
```

- `{id}` 가 비어 있으면 한 번 묻고, `git config user.name` 설정을 안내한다. `handoffs/{id}/` 가 없으면 만든다.

## 1. 오늘 변경 파악

```bash
node packs/core/bin/repo-activity.js              # workspace.json repos + 워크스페이스, 본인·푸시 기준 (오늘 0시 이후)
```

- **완료 커밋 = 본인 author + 푸시됨** 만 적는다. **미푸시 커밋·미커밋 변경은 "진행 중"** 으로 적는다. 남의 커밋은 기록하지 않는다.
- 대화에서 내린 결정 · 사용자 선택 · 알아낸 원인도 모은다.

### 진행 중 코드: 작업 브랜치

미푸시 커밋·미커밋 변경이 있는 repo 는 **이 PC 에만 있어** 다른 사람이 이어받을 수 없다. repo 마다 묻는다:
"repos/<repo> 의 진행 중 작업을 작업 브랜치로 push 해 둘까요? (다른 사람이 인수할 수 있게)"

- 예: 그 repo 의 브랜치 규칙을 따라 작업 브랜치를 쓴다. 기본 브랜치(main·develop 등)에 직접 push 하지 않는다. 미커밋 변경은 사용자가 승인한 것만 커밋한다.
- 아니오: push 하지 않고 "이 PC 에만 있음" 으로 적는다.

브랜치 운영이 통합 브랜치 직접(`workspace.json` `vars.gitlab.branchMode` 가 `trunk`)이면 작업 브랜치를 만들지 않는다. 묻는 말도 바꾼다: 검사를 통과한 커밋만 "통합 브랜치에 push 할까요?" 로 묻고, 통과하지 못한 변경은 push 하지 않고 "이 PC 에만 있음 · push 안 함 이유" 로 적는다.

## 2. 작업별 기록 (`topics/<작업>.md`)

```bash
node packs/core/bin/handoff.js topic       # 이름 후보 + 기존 기록
```

- **이름**: 티켓 번호(`IM-360`) → 요구사항 ID(`REQ-ORD-012`) → 기능·화면 이름(`주문-목록`) 순. 티켓이 없는 초반 개발은 기능·화면 이름으로 한다.
- **같은 일이면 기존 기록에 이어 쓴다.** 기능 기록(`주문-목록`)에 나중에 QA 티켓이 생기면 새 기록을 만들지 않고 `관련:` 에 티켓을 더한다.
- 오늘 한 작업마다 하나씩. 형식:

```markdown
# 주문-목록
관련: REQ-ORD-012 · IM-401
상태: 진행 중            (진행 중 | 완료 | 보류)
마지막: 2026-09-30
한 줄: 페이지네이션 서버 구현 완료, 화면 연결 남음

## 요약
(지금까지의 핵심: 무엇을 왜 이렇게 했나, 지켜야 할 결정, 함정. 날짜가 쌓이면 여기를 갱신한다)

## 완료 조건
- [x] 서버 페이지네이션 테스트 통과
- [ ] 화면 연결 (REQ-ORD-012)
- [ ] 핸드오프 갱신
- [~] 정렬 기준 (사용자 결정 대기)
- [>] 2026-11-02 장중 응답 시간 측정 (그날 전에는 할 수 없음)

## 지킬 것
- 목록 API 응답은 기존 응답 봉투 관례대로 (packs/project/ 참조)

## 2026-09-30
- 한 일 · 결정(사용자 선택) · 원인 · 검증 결과(표) · 바꾼 파일 · 커밋 · 브랜치
- 남은 일은 위 `## 완료 조건` 에 [ ] 로 둔다 (TODO.md 로 옮기지 않는다)
```

- 머리 5줄(제목 · 관련 · 상태 · 마지막 · 한 줄)은 도구가 색인을 만드는 데 쓴다. 매번 갱신한다.
- **완료 조건**: 작업을 시작할 때 "끝났다" 의 기준을 3~7개 적고, 끝낸 항목은 `[x]`, 사용자 결정을 기다리는 항목은 `[~]`, 정한 날짜 전에는 할 수 없는 항목은 `[>] YYYY-MM-DD 할 일`(날짜 예약)로 바꾼다. 이번 세션에 손댄 작업에 미완(`[ ]`) 항목이 남은 채 끝내려 하면 훅이 끝내기 전에 처리·보고하게 한다 (세션마다 작업당 한 번. `[~]` 와 날짜 전의 `[>]` 는 세지 않는다). 날짜 예약은 그날이 되면 세션 시작 줄 · 진행 중 작업 알림 · 재개 보고에 「오늘 예정」 으로 뜨고 미완으로 센다. 날짜가 지나도 `[>]` 면 「지난 예약」: 했으면 `[x]`, 미루면 날짜를 고친다. `handoff.js check` 는 진행 중인데 이 절이 없거나 비어 있으면, `상태:` 줄이 없으면, `[>]` 에 날짜가 없거나 잘못됐으면 ✖ 로 막고, 지난 예약은 ⚠ 로 알린다. 미완 업무를 셀 근거가 없어지기 때문이다.
- **지킬 것**: 이 작업에서 놓치기 쉬운 규칙·함정 1~3줄. 요청마다 다시 보여 주므로 짧게. 없으면 절을 비워 둔다.
- 파일이 커지면(40KB) 오래된 날짜 섹션을 `## 요약` 에 녹이고 지운다. 원문은 git 이력에 남는다.

## 3. 주간 기록 (`YYYY-Www.md`): 짧게

파일이 있으면 **다른 날짜 섹션은 그대로 두고** 오늘 `## YYYY-MM-DD` 섹션만 추가·교체한다.

```markdown
## 2026-09-30
- [주문-목록](topics/주문-목록.md): 페이지네이션 서버 구현 완료 (커밋 `a1b2c3d`), 화면 연결 남음
- [IM-360](topics/IM-360.md): 원인 확정, MR api !307 등록
```

**작업마다 한두 줄 + 링크만.** 자세한 내용은 작업별 기록에 쓴다 (하루 3KB 넘으면 검사에서 막힌다).

## 4. `LATEST.md`: 지금 상태 (4KB 이내)

```markdown
# 마지막 핸드오프 (YYYY-MM-DD)

## 오늘 핵심
(작업별 한 줄 + 링크)
## 진행 중 / 미커밋
## 작업 브랜치
(repo 마다 `- repos/<repo>: <브랜치> (push 됨 | 이 PC 에만 있음): <무엇>`. 없으면 "없음")
## 사용자 결정 (오늘)
## 남은 작업
미완 업무는 작업별 기록(진행 중 + 완료 조건 [ ])이 정본, 사용자가 등록한 할 일은 `TODO.md` (여기에 목록을 복제하지 않는다)
```

- 직전 사이클 내용은 쌓지 않는다 (작업별 기록 · 주간 기록에 있다).

## 5. `TODO.md`: 사용자가 등록한 할 일

- **사용자가 "TODO 에 넣어줘" 라고 할 때만** 넣는다. 끝내지 못한 업무를 에이전트가 알아서 옮기지 않는다. 미완 업무는 작업별 기록의 `## 완료 조건` 에 `[ ]` 로 남기면 재개 · 팀 현황 · 인계가 그것을 본다.
- 형식: `- **무엇** · 어디서 이어서 ([작업](topics/<작업>.md))` 한 줄. 인수한 항목은 `← {원래 사람} 에게서 인수 (날짜)`.
- 항목을 지우는 것도 사용자가 정한다. 끝난 것 같으면 지울지 묻는다.
- **"TODO 정리" 요청**: 번호를 붙인 목록을 보이고 항목마다 "끝남 · 아직 진행 중 · 그대로" 를 고르게 한다. 끝남은 줄을 지우고, 아직 진행 중인 업무는 작업별 기록의 `## 완료 조건` 에 `[ ]` 로 옮길지 묻는다 (예면 옮기고 TODO 에서 뺀다). 답 없는 항목은 그대로 둔다. 바로 공유하려면 이어서 핸드오프할지 묻는다.

## 5.5 로드맵 (`handoffs/PLAN.md`, 팀 공용)

- 오늘 단계·영역의 하위 작업을 끝냈으면 그 칸을 ✔ 로, 단계를 끝냈으면 단계 상태를 ✔ 와 완료 날짜로, 다음 단계를 ▶ 와 시작 날짜로 바꿀지 **사용자에게 묻고** 고친다. 상태는 사람이 정한다.
- 단계를 시작하면 그 단계의 하위 작업을 `## <단계 이름>` 절에 쪼갠다 (영역이 있으면 표, 없으면 체크 목록). 미리 다 쪼개지 않는다.
- 영역·하위 작업 수가 바뀌면 `## 분모 변경` 에 `- YYYY-MM-DD · 무엇 n → m · 사유` 한 줄.
- **이슈형**(`## 이슈` 표가 있는 로드맵): 단계 대신 오늘 다룬 이슈의 줄을 고칠지 묻는다. 새 이슈는 한 줄 추가(첫 상태 · 시작 날짜), 상태가 바뀌면 상태와 갱신 날짜, 운영에 반영했으면 운영 반영 날짜. 상태 이름은 그 절의 `상태:` 줄에 있는 것만 쓴다.
- 고쳤으면 커밋에 `handoffs/PLAN.md` 도 넣는다. 아래 `check` 가 갱신 누락을 ⚠ 로 알린다.

## 6. 검사 · 색인 · 보관

```bash
node packs/core/bin/handoff.js archive     # 8주 지난 주간 기록을 archive/ 로 (지우지 않는다)
node packs/core/bin/handoff.js index       # INDEX.md (작업 색인) 다시 만들기
node packs/core/bin/handoff.js check       # 크기 · 흩어진 파일 검사
node packs/core/bin/tidy.js --count --new  # 정리 후보 (이번 작업에서 방향이 바뀌어 남은 파일)
```

- `check` 가 ✖ 를 내면 고친 뒤 다시 검사한다: 크기는 줄이고(LATEST · 오늘 섹션을 작업별 기록으로), 작업 기록은 머리와 완료 조건을 채운다. ⚠ 는 보고에 적는다.
- `handoffs/{id}/` 바로 아래에 작업 메모 파일을 새로 만들지 않는다. 작업 메모는 `topics/` 로.

## 7. 커밋 · 푸시 (워크스페이스 repo 한정)

- 핸드오프를 하기로 한 사용자 답이 **이 기록 커밋·푸시까지의 승인**이다. 범위는 `handoffs/{id}/` 와, 이번에 고쳤으면 팀 공용 기록 `handoffs/PLAN.md`(5.5) · `handoffs/MODELS.md`(team 스킬의 모델 조사)뿐이다 (명시한 경로만 스테이징, `git add -A`·`.` 금지).
- **비밀값은 적지 않는다.** 명령 결과 · 오류 로그 · 설정을 옮길 때 토큰 · 키 · 비밀번호 · 접속 주소의 인증 부분은 `***` 로 가린다. 워크스페이스 커밋 훅이 비밀값 모양을 찾으면 커밋을 막는다 (값은 찍지 않고 파일:줄만).
- 커밋 메시지: `docs: YYYY-MM-DD 핸드오프 ({오늘 핵심 한 줄})`
- upstream 이 있으면 먼저 받고 push 한다: `git pull --rebase --autostash` → `git push`. 실패하면 멈추고 보고한다.
- **다른 repo 는 커밋하지 않는다.** 미커밋이 있으면 보고만 한다.
- 팀 전체 요약 파일은 만들지 않는다 (예전 `handoffs/INDEX.md`). 팀 현황은 `team-status` 스킬이 그때그때 모은다.

## 8. 보고

```
핸드오프 완료 (YYYY-MM-DD)
- 작업별 기록: topics/<작업>.md … (새로 · 이어 씀)
- 스냅샷: handoffs/{id}/LATEST.md · 미완 작업 {n}건 · 내 TODO {m}건
- 로드맵: {node packs/core/bin/plan.js --short} (이번에 고친 칸이 있으면 무엇을)
- 검사: ✔ 또는 ⚠ 내용
- 정리 후보: {tidy.js --count --new 한 줄} (0 이 아니면 tidy 스킬로 정리할지 묻는다)
- 작업 브랜치: {repo: 브랜치 (push 됨 | 이 PC 에만 있음)} 또는 "없음"
- 기록 커밋: {SHA} (푸시 완료 / 실패 사유)
- 다른 repo 미커밋·미푸시: {요약 또는 "없음"}
```

- 보고 끝에 **「로드맵을 볼까요?」** 를 선택지 질문으로 묻는다 (보기 · 안 보기, 글 질문으로 묻지 않는다). 보기를 고르면 `node packs/core/bin/plan.js` 를 돌려 출력(흐름도 · 지금 단계 표 · 이번에 생긴 것 · 다음)을 그대로 붙인다. 안 보기를 고르거나 답이 없으면 붙이지 않는다.

> Stop 훅(`packs/core/hooks/handoff-reminder.js`)은 push 뒤 오늘 핸드오프가 없으면 "핸드오프 할까요?" 를 묻게 한다. 사용자가 "나중에" 라고 하면 워크스페이스 루트 `.handoff-snooze` 첫 줄에 세션 id(또는 오늘 날짜)를 적는다.
