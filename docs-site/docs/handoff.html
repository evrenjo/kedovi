원본 handoff.md

handoff(기록) · resume(내 작업 재개) · takeover(남의 작업 인수) · 팀 현황.

작업 기록은 워크스페이스 repo 의 handoffs/<id>/ 에 남고 push 로 팀에 공유된다 (<id> = 워크스페이스의 git config user.name). 각자 자기 폴더만 쓴다.

할 때에이전트에게하는 일
하루 끝"핸드오프"작업별 기록(완료 조건의 [ ] = 미완 작업) · LATEST.md(마지막 상태) · 주간 기록을 쓰고 commit · push (push 전에 pull). 진행 중 코드가 이 PC 에만 있으면 작업 브랜치로 push 할지 묻고 「작업 브랜치」에 적는다
다시 시작"재개" (resume, 본인 전용)내 LATEST · 미완 작업 · TODO · 최근 활동 · repo 상태 보고. 세션을 열면 마지막 핸드오프가 한 줄로 먼저 뜬다 (세션 시작 훅)
팀 상황"팀 현황" 또는 kedovi team모두의 마지막 핸드오프 · 핵심 · 진행 중 · 작업 브랜치 · 미완 작업 · TODO · N일째 갱신 없음
인수인계"인수인계 <id>" (takeover) 또는 kedovi team <id>그 사람 기록을 보고 → 고른 미완 작업은 내 작업별 기록으로, 고른 TODO 항목은 내 TODO.md 로 옮긴다 (← <id> 에게서 인수 (날짜)). 그 사람 폴더는 건드리지 않고, 팀 현황에 "인수됨" 으로 보인다. 작업 브랜치가 push 돼 있으면 그 브랜치에서 이어 간다
  • 합류: 팀원은 kedovi install 때 "팀에 합류 기록을 올릴까요?" 에 예를 누르면 handoffs/<id>/ 가 push 돼 팀 현황에 "합류함" 으로 바로 보인다. 리더는 kedovi init 때 만들어진다.
  • 명단(선택): 리더가 kedovi team add <id…> 로 명단을 두면 팀 현황에 "미합류"(명단에만 있음)·"명단에 없음" 도 보인다. kedovi team restrict on 이면 명단 밖 사람은 kedovi start 가 멈춘다. 이것은 실수 방지용이다. claude·codex 를 직접 실행하면 우회되고 id(git user.name)도 본인이 바꿀 수 있다. 접근 통제는 GitLab·GitHub 멤버 권한으로 한다.
  • 기록은 작업별로. 자세한 내용은 handoffs/<id>/topics/<작업>.md(티켓 번호 → 요구사항 ID → 기능·화면 이름)에 이어 쓰고, 주간 기록에는 날짜마다 작업별 한두 줄만 남긴다. 그래서 기록이 수십만 자로 불어나지 않고, 다음에 같은 일을 할 때 그 작업 기록만 읽으면 된다.
  • 크기 검사 · 찾기 · 보관: kedovi handoff check(LATEST 4KB · 하루 3KB), find <티켓·기능>(모든 사람 기록에서 파일:줄), archive(8주 지난 주간 기록 보관), index(작업 색인). 핸드오프가 끝날 때 돌고, 기록이 크면 세션 시작 알림이 알려 준다.
  • 미완 작업과 TODO: 남은 일의 정본은 작업별 기록이다 (상태 진행 중 + ## 완료 조건 의 [ ]). TODO.md 는 사용자가 "TODO 에 넣어줘" 할 때만 쓰는 개인 할 일이고, 에이전트가 미완 업무를 알아서 옮기지 않는다. "TODO 정리해줘" 면 목록을 보이고 항목마다 끝남 · 진행 중(작업 기록으로 옮길지) · 그대로를 고르게 한다. kedovi handoff check 는 진행 중인데 완료 조건이 없거나 비었거나 상태: 줄이 없는 기록을 ✖ 로 막는다.
  • 완료 조건: 작업 기록의 ## 완료 조건 에서 끝낸 항목은 [x], 사용자 결정을 기다리는 항목은 [~], 정한 날짜 전에는 할 수 없는 항목은 [>] 2026-11-02 할 일(날짜 예약). 이번 세션에 손댄 작업에 [ ] 가 남은 채 끝내려 하면 훅이 한 번 처리·보고하게 한다 ([~] · 날짜 전의 [>] · 손대지 않은 작업은 보지 않는다).
  • 날짜 예약: 그날이 되면 세션 시작 줄 · 진행 중 작업 알림 · 세션 브리핑 · 재개 보고에 「오늘 예정」 으로 뜨고 미완으로 센다. 지나도 [>] 면 「지난 예약」 으로 알린다 (했으면 [x], 미루면 날짜를 고친다). 날짜가 없거나 없는 날짜면 kedovi handoff check 가 막는다.
  • 이미 커진 기록: handoff-organize 스킬("핸드오프 정리")이 후보를 뽑아 작업별 기록으로 나누고 원본은 보관한다 (지우지 않는다).
  • 팀 현황은 git fetch 후 원격 기준으로 읽어 작업 폴더를 바꾸지 않는다. 아직 push 하지 않은 핸드오프는 보이지 않는다.

로드맵#

프로젝트 전체의 큰 단계와 상태는 handoffs/PLAN.md 하나에 둔다 (팀 공용). kedovi init 이 유형 · 진행 방식 · 스택마다 기본 단계로 만들고, 없던 워크스페이스는 kedovi upgrade 가 만든다 (사람이 고친 것은 그대로).

진행 방식 (workspace.json 의 project.approach, kedovi approach 로 바꾼다)

진행 방식새 워크스페이스 기본동작

  • 스프린트 로드맵: 스프린트 계획 → 구현 → 데모 → 회고를 반복한다. ## 이번 스프린트 에 목표(데모에서 보여 줄 한 줄) · 끝 날짜(선택) · 기능 체크 목록을 두고, 체크 목록이 구현 단계의 하위 작업이 된다. 데모는 실행 방법(명령 · 주소 · 화면)과 함께 돌아가는 결과를 보여 주고 확인받는다. 회고는 ## 지난 스프린트 에 - 날짜 · S<번호> 목표 · 잘 된 것 · 바꿀 것 한 줄 남기고 백로그에서 다음 스프린트 후보를 추천한다. 끝 날짜가 지났는데 데모 전이면 ⚠. 스택 단계(데이터 설계 · 화면설계)는 따로 두지 않고 「스프린트 계획」 체크 목록에 이번 스프린트의 스키마 · 화면 변경 여부로 둔다. 운영·고도화도 다른 유형과 같은 스프린트다.
  • 화면설계 · 데이터 설계에서 이번 스프린트에 넣지 않는 기능은 화면 목록 · 엔티티 목록에 「다음 스프린트」 로 적는다 (kedovi screens check · kedovi datamodel check 가 누락으로 세지 않는다).
  • 신규 구축은 진행 방식과 상관없이 첫 단계가 「아이디어 · 전체 그림」 이다: 무엇을 왜 만드는지 사용자와 대화해 기능 지도 · 하지 않을 것 · MVP 범위(워터폴이면 전체 범위)를 정한다 (idea 스킬). 기획이 이미 있으면 상태를 ✔ 건너뜀 으로 두고 넘어간다. 스프린트를 되돌릴 때 이 단계는 그대로 둔다.
  • 진행 방식이 없는 옛 워크스페이스는 전체처럼 동작하고, kedovi upgrade 가 고르는 법을 한 줄 알린다. 바꾸면 기본 단계 그대로이고 끝낸 단계가 없는 로드맵만 새 뼈대로 바꾼다.

바꾸기단계형 로드맵을 이슈형으로 바꾸면 맨 앞에 ## 이슈 를 끼우고 전 단계 표는 아래 「이슈형으로 바꾸기 전 단계」 에 남긴다 (## 이슈 가 있으면 단계 표는 읽지 않는다)

기본 단계는 SDLC 7단계 · 행정기관 정보시스템 구축·운영 지침 · 레거시 전환 가이드 · NIA ISP·ISMP 공통가이드의 흔한 구성을 따른다. 프로젝트에 맞게 고쳐 쓴다 (첫 세션에서 에이전트가 고칠지 묻는다).

스택에 따라 끼우는 단계: (아키텍처·)설계와 구현 사이에 넣는다. 화면이 보여 줄 데이터 · 저장 구조가 먼저라 데이터 설계가 앞이다.

DB (db · stack-postgres 등)데이터 설계 (테이블 정의서 · ERD)datamodel
화면 (웹 · 모바일 · 데스크톱 · 워치 · TV)화면설계 (화면설계서)screens
  • 예 (차세대 + PostgreSQL + React): AS-IS 분석 → 범위·계획 → 요구사항 → 아키텍처·설계 → 데이터 설계 → 화면설계 → 구현 → 테스트 → 데이터 이관 → 전환 → 안정화.
  • 스프린트는 단계를 늘리지 않고 「스프린트 계획」 체크 목록에 스키마 변경 여부 · 화면 변경 여부를 둔다. 이슈형은 단계가 없다.
  • 0.63 전 운영·고도화 기본 단계(접수 → 분석 → 구현 → 테스트 → 배포) 그대로인 로드맵은 kedovi upgrade 가 바꾸지 않는다. kedovi approach · kedovi type 으로 바꿀 때만 새 뼈대가 된다.
  • 그 단계에 들어가면 kedovi plan · 브리핑이 맡는 스킬을 알려 주고, 에이전트는 그 스킬의 진행 방식 합의부터 한다.
  • 기본 단계 그대로(<!-- kedovi:preset -->)인 PLAN.md 는 kedovi upgrade 가 스택 단계를 더한다 (상태 · 날짜는 그대로). 사람이 고친 PLAN.md 는 건드리지 않고 kedovi plan · kedovi handoff check 가 「스택에 DB 가 있는데 데이터 설계 단계가 없습니다」 를 ⚠ 로 알린다.
  • 상태만 사람이 정한다: ✔ 완료 · ▶ 진행 · ○ 미착수 · ◇ 미분해. 숫자(완료 n / 전체 N · 이번에 생긴 커밋 · 새 파일 · ID 수)는 kedovi plan 이 센다. 퍼센트로 합치지 않고, 세지 않은 숫자는 쓰지 않는다.
  • 하위 작업은 그 단계를 시작할 때 ## <단계 이름> 절에 쪼갠다. 영역이 있으면 표(영역 × 하위 작업), 없으면 체크 목록.
  • 분모가 바뀌면 ## 분모 변경 에 - 날짜 · 무엇 n → m · 사유 한 줄. 계획이 늘어도 진행률이 정직하게 남는다. 위 · 아래 어느 쪽에 더해도 kedovi plan 은 날짜가 가장 늦은 줄을 「최근」 으로 보인다.
  • 보이는 곳: kedovi start 세션 브리핑에 흐름도 · 지금 단계 표, 재개 보고 · 팀 현황에 한 줄, 단계를 끝낸 보고에 전체 블록(흐름도 · 표 · 이번에 생긴 것 · 다음), 핸드오프가 끝나면 「로드맵을 볼까요?」 를 선택지 질문(보기 · 안 보기)으로 묻고 보기면 전체 블록, PLAN.md 가 바뀐 push 는 팀 방 알림.
  • 갱신 누락: kedovi handoff check(핸드오프 때 돈다)가 기본 단계 그대로 · 진행 단계 없음 · 하위 작업이 다 끝났는데 단계가 그대로 · 스택에 맞는 단계 없음 같은 것을 ⚠ 로 알린다.
  • ID 를 세려면 workspace.json 의 vars.plan.ids 에 접두사를 둔다 (예: REQ,TC).
  • 설정 잠금이어도 팀원이 handoffs/PLAN.md 는 커밋할 수 있다.
  • 모두가 고치는 공용 요약 파일은 두지 않는다 (push 충돌 원인). 예전 handoffs/INDEX.md 는 더 쓰지 않는다.
