킷 개발

원본 kit-dev.md

킷 repo 를 고치는 사람을 위한 문서다. 킷 문서 사이트(docs-site/)의 「킷 개발」 묶음에 있다. 작업 지침은 AGENTS.md, 모델 추천 갱신 절차는 모델 카탈로그 관리.

새 팩 추가#

여러 프로젝트에 두루 쓸 규칙이면 킷의 팩으로 만든다. 모든 워크스페이스가 kedovi upgrade 로 받는다.

  1. 킷 repo 에 packs/<이름>/pack.json 을 만든다 (name · title · summary · description · category · requires).
  2. rules/ · skills/ · hooks.json · bin/ 을 필요한 만큼 둔다. 종류(category)에 따라 붙는 조건이 정해진다 (docs/packs.md).
  3. 스택 팩이면 packs/core/stacks.json 에 감지 조건을 더한다.
  4. npm test 로 검사하고(생성 · 죽은 참조 · 예산 · 금지 문자열), npm run docs 로 팩 목록을 다시 만든다.
  5. 커밋 · push 하면 배포된다. 각 워크스페이스는 kedovi upgrade.

스택 목록 (stacks.json)#

위치: packs/core/stacks.json

repo 를 보고 스택을 감지하는 조건이다. 새 기술은 여기에 한 줄을 더하면 감지되고 layer 공통 규칙이 붙는다. 전용 규칙까지 주려면 stack 팩을 만들고 그 항목에 "pack" 을 적는다.

{ "id": "fastapi", "label": "FastAPI", "layer": "backend", "pack": "stack-fastapi",
  "detect": [{ "files": ["pyproject.toml", "requirements*.txt"], "contains": "fastapi" }] }
  • detect 는 조건 목록(하나라도 맞으면 감지). 조건 = 파일 이름(* 허용, 깊이 4 까지) + 선택적 내용 정규식. 소스 파일 표식처럼 깊은 곳을 봐야 하면 "depth": 9 처럼 적는다(최대 10). 깊은 조건은 느리니 빌드·설정 파일 조건 뒤에 둔다.
  • 프로젝트 전용 조건(사내 라이브러리 좌표)은 킷이 아니라 워크스페이스의 workspace.json stackHints 에 둔다 (kedovi detect --hint).
  • 감지 결과는 workspace.json 의 repos[].stacks 에 저장되고 사람이 고칠 수 있다 (kedovi detect). 멀티모듈 repo 는 스택별 모듈이 repos[].stackPaths 에 함께 저장되고, AGENTS.md repo 별 규칙 표에서 layer·stack 팩 규칙마다 모듈 경로가 붙는다.
  • parent 를 적으면 그 프레임워크의 세부가 된다 (예: spring-webflux → spring). 세부는 부모의 layer·팩을 함께 받는다.
  • packSkipWith 에 적은 스택과 함께 감지되면 전용 팩을 붙이지 않는다 (예: Flutter · React Native 앱 안의 android/ 에는 stack-android 를 붙이지 않는다).
  • languageIgnore 에 적은 폴더(그 스택이 감지된 모듈 기준)는 언어를 셀 때 뺀다 (예: Flutter 앱의 ios/ · windows/ 실행 파일 때문에 Swift · C++ 규칙이 붙지 않게).
  • 감지 조건마다 근거(공식 문서 URL)는 docs/stack-catalog-sources.json 에 둔다.

언어 목록 (stacks.json 의 languages)#

repo 의 언어는 소스 확장자 수로 감지한다 (5개 이상이면서 감지 대상 소스의 10% 이상이거나, 절반을 넘거나, 유일한 언어). 결과는 workspace.json 의 repos[].languages 에 저장되고 kedovi detect · kedovi upgrade 가 채운다 (비어 있으면 다시 감지: 새로 만든 빈 repo 에 코드가 생긴 경우). 빌드 결과물 · 내려받은 의존성 폴더(node_modules · Pods · .next 등)와 도구 설정 파일(*.config.js · .d.ts)은 세지 않는다. kedovi detect 에서 건너뛴 repo 는 false 로 기록돼 다시 채우지 않는다. 언어가 하나라도 있으면 clean-code 팩(언어 공통)이, 언어마다 그 항목의 pack(lang-*)이 그 repo 에 붙는다. pack 이 없는 언어(TypeScript · JavaScript · Go · C#)는 공통 규칙만 받는다.

{ "id": "kotlin", "label": "Kotlin", "ext": ["kt"], "pack": "lang-kotlin" }
  • 새 언어는 여기에 한 줄과 category: "lang" · "languages": ["<id>"] 팩을 더한다. 두 곳이 어긋나면 npm test 가 잡는다.
  • 확장자가 두 언어에 걸치면(.h) 세지 않는다. 빌드 스크립트(.kts)도 세지 않는다.
  • 규칙 근거(스타일 가이드 · 책 · 논문)는 팩 description 끝의 「근거:」 에 적는다 (팩 종류 쪽에 그대로 나온다).

AI 도구(CLI) 추가#

시작 도구는 명단제다 (지금은 Claude Code · Codex). 다른 CLI(Gemini CLI 등) 요청이 오면 아래 순서로 넣는다. 감지는 한 줄이지만 생성물이 도구마다 달라서 한 세트를 같이 만들어야 한다.

순서어디무엇
1bin/kedovi.js AGENTS명령 이름 · 설치 명령 · 모델 플래그. "쓰는 AI" 선택지와 ARG_PRESETS(자주 쓰는 실행 인자)도 여기
2packs/core/lib/cli.js설치 여부·실행 파일 찾기 (findCli)
3bin/kit.js그 도구의 설정 파일 생성: 규칙 파일 위치, 훅 등록 형식(hookGroups), 역할 에이전트 파일, 시작 도구 판정(startToolOf)
4packs/core/lib/hook.js · packs/core/hooks/*.js훅 입출력 계약이 다르면 --agent=<도구> 분기. 지원하지 않는 이벤트는 hooks.json 의 agents 로 제외
5packs/core/models.jsontools.<도구> 모델 목록 · profiles.*.<도구> 역할별 추천 (조사 절차는 model-catalog.md)
6packs/core/bin/delegate.js · cross-review.js그 도구의 비대화형 실행(<명령> -p 류)으로 위임·교차 검토
7packs/core/bin/doctor.js · bin/gateway.js진단 항목 · 게이트웨이 모델을 그 도구 모델명으로 잇기
8docs/pack-making.md 대응표 · docs/workflow.md · README도구별 차이 표와 흐름도
9bin/selftest.js생성물·훅·위임 검사에 그 도구 케이스 추가
  • 규칙·스킬은 도구 중립이라 AGENTS.md 를 읽는 도구면 1~3 만으로도 규칙은 먹는다. 훅·역할 에이전트·위임은 4~6 이 있어야 한다.
  • 다른 회사 모델만 필요하면 도구를 더하지 않는다. AI 게이트웨이로 연결하면 Claude Code 안에서 그 모델을 고를 수 있다.

문서 사이트 앱#

문서 사이트(킷 가이드 · 기획 repo · 현황판)의 화면은 한 앱이다. 빌드 도구 없이 클래식 스크립트로 넣는다 (file:// 로 연 현황판도 돌게, 브라우저는 file:// 에서 ES 모듈을 막는다).

할 일방법
화면 고치기
문서 사이트 packs/core/assets/docs-site/src/*.js · ERD 뷰어 packs/datamodel/assets/erd/src/*.js · 화면설계서 뷰어 packs/screens/assets/storyboard/src/*.js (기능별 파일, 이름 순으로 이어져 site.js · erd.js · storyboard.js 하나씩이 된다).
더 보기
문서 사이트와 ERD 가 같이 쓰는 부품(사이드바 머리 줄)은 packs/core/assets/docs-site/shared/ 에 두면 두 파일 앞에 들어간다. 스타일은 각 폴더의 css. 문서 사이트는 npm run docs 로 이 가이드에서, 뷰어는 npm run test:site 의 시험 사이트에서 확인
외부 라이브러리
vendor.json 에 이름 · 버전(나온 지 2주 넘은 것) · 넣을 파일을 적고 npm run vendor.
더 보기
공개 npm 에서 받아 packs/core/assets/docs-site/vendor/ 에 라이선스와 함께 둔다. 생성기(Node)가 쓰는 것(markdown-it)은 bundles 로 적으면 esbuild 가 packs/core/lib/vendor/ 에 파일 하나로 묶는다 (딸린 의존 버전은 vendor-lock.json). 받은 파일이 맞는지만 볼 때는 npm run vendor:check. 새 라이브러리는 THIRD_PARTY_NOTICES.md 에도 적는다
쪽 파일생성기(packs/core/lib/mdsite.js)가 쪽마다 본문 HTML(.ds-body) 과 쪽 정보(script#ds-page)를 쓴다. 앱은 그 둘로 그리고, 쪽을 옮길 때도 다음 쪽 파일에서 둘만 꺼낸다
시험화면은 npm test 가 보지 않는다. npm run test:site 가 이 PC 의 Chrome 을 화면 없이 띄워 이동 · 검색 · 그림 · 인쇄 · 좁은 화면 · file:// · 필기(마우스 · 손가락 · 펜) · 근거 패널 · ERD 뷰어 · 화면설계서 뷰어를 본다. 실기기(아이패드 · 갤럭시) 펜 감도는 직접 본다
