스킬

이름설명
architecture시스템 구성도(서비스 · DB 와 스키마 · Redis · 메시지 큐 같은 미들웨어 · 외부 서비스 · 서버 사양)를 단계별(1차 · 2차 …) mermaid 그림과 표로 만든다. "구성도", "아키텍처 그림", "시스템 구성", "서버 구성", "인프라 구성", "서버 사양" 요청에 쓴다.
autopilot자율완주 모드: 묻고 멈추는 대신 결정 필요 항목은 목록에 표시만 하고, 할 수 있는 구현은 끝까지 한 뒤 검증·핸드오프·커밋(푸시 없음)까지 마친다. "알아서 끝까지", "자리 비운다" 요청에 쓴다.
common-practice흔한 방식 · 업계 관례 · 표준을 웹 검색으로 확인해 출처와 함께 비교해 답한다. 사용자가 "아닌가?", "보통 ~하던데", "다른 데는 어떻게 해?", "일반적으로", "표준이 뭐야", "찾아봐줘", "검색해봐" 라고 묻거나 다른 서비스 화면 · 문서를 예로 들며 우리 것과 다르다고 할 때, 또는 내가 "보통은 ~" 이라고 말하려 할 때 쓴다.
cross-review다른 벤더의 에이전트에게 읽기 전용 교차 리뷰(두 번째 의견)를 받는다: Claude Code 세션이면 Codex, Codex 세션이면 Claude Code 를 비대화형으로 돌린다. "교차 리뷰", "다른 모델 의견", "codex 한테도 봐 달라" 요청에 쓴다.
debate토론 모드. 여러 모델(다른 회사 모델 포함 2~4개)이 같은 문제를 따로 보고, 이름을 가린 주장 목록에 서로 동의 · 반대해 갈린 것만 다시 본다. 코드 리뷰 · 설계 · 요구 · 문서 · 원인 분석 어떤 작업이든. "토론해줘", "토론 모드", "여러 모델로 봐줘", "다른 모델들한테도", 또는 결과가 마음에 안 든다 · 맞는지 모르겠다는 말에 쓴다.
doctor워크스페이스 셋업·환경(Node·git·repos/ 의 repo·훅 경로·kit 생성물·에이전트 CLI)을 진단한다. 처음 받았을 때나 뭔가 깨졌을 때 쓴다.
go이 워크스페이스에서 작업을 시작한다: 본인 핸드오프·repo 상태를 확인하고, 요청을 다시 정리해 영향 범위·할 일·검증 계획·안 할 것을 먼저 제시한 뒤 착수한다. "시작", "작업하자", 새 요구사항을 받았을 때 쓴다.
handoff작업을 마무리하고 본인 핸드오프(작업별 기록 · 주간 기록 · LATEST · TODO)를 남긴다. "핸드오프", "마무리", "오늘 정리" 요청에 쓴다. "TODO 에 넣어줘", "TODO 정리" 도 이 스킬 5절을 따른다.
handoff-organize이미 커진 본인 핸드오프 기록(수십만 자 주간 기록 · 흩어진 메모 파일 · 쌓인 색인)을 작업별 기록으로 나눠 정리한다. 원본은 지우지 않고 보관한다. "핸드오프 정리", "기록 정리", "핸드오프가 너무 길다" 요청에 쓴다.
idea신규 구축의 첫 단계. 무엇을 왜 만들려는지 사용자와 충분히 대화해 전체 그림(누구 · 문제 · 핵심 흐름 · 기능 지도 · 하지 않을 것)을 그리고, MVP(첫 스프린트) 또는 워터폴 범위를 정한다. "아이디어 정리", "무엇을 만들지", "전체 그림", "MVP 정하기", "기획 시작" 요청과 로드맵 「아이디어 · 전체 그림」 단계에 쓴다.
import기존 AI 작업 폴더(예전 지침 파일 · 룰 · 메모 · 핸드오프 · 스크립트)를 이 워크스페이스로 옮긴다. 먼저 훑어 계획을 보여 주고 승인 뒤에 옮긴다. "기존 폴더 가져와", "이관", "예전 설정 옮겨줘" 요청에 쓴다.
kedovi워크스페이스 설정을 바꾸거나 확인하는 요청을 kedovi 명령으로 처리한다 (비밀값(토큰) 확인 · 옮기기 · 텔레그램 알림 · 팀 공지 · 모델·프로필·AI 연결 방식(구독·게이트웨이)·시작 도구·규칙 켜고 끄기·팀 명단·설정 수정 권한·repo 추가·스택 감지·진단·팀 현황·킷 업그레이드 · 팩 켜기 · 진행 방식(스프린트 · 전체 · 이슈형) · 유형 바꾸기 · 로드맵 보기 · 문서 사이트 · 기획 문서 ID 찾기 · 화면설계 · 데이터 설계 검사).
resume이 워크스페이스로 돌아왔을 때 본인 마지막 핸드오프·미완 작업·TODO·최근 활동·repo 상태를 한 번에 파악해 보고한다. 본인 작업 재개 전용이다. "재개", "어디까지 했지", "상태 파악" 요청에 쓴다.
review현재 변경사항(git diff)을 코드 리뷰한다: 결함·누락·보안·계약 동기화·검증 누락을 짚고 수정안을 낸다. "리뷰", "검토해줘" 요청에 쓴다.
takeover다른 개발자의 핸드오프 기록을 받아 그 사람 작업을 이어받는다(인수인계). 팀장이 배정하거나 팀원이 빠질 때 쓴다. "인수인계", "<id> 작업 인수", "<id> 일 이어받기" 요청에 쓴다. 본인 작업 재개는 resume.
team
역할 에이전트(분석·설계·설계 문서·구현·테스트·리뷰·문서화와 팩·프로젝트가 더한 역할)를 불러 일을 나눠 진행한다.

자동 모드면 작업마다 역할과 모델을 골라 구성표를 알리고 시작한다. 버그 수정·기능 추가·리팩터링·레거시 분석·리뷰처럼 여러 단계나 여러 repo 에 걸친 작업에서, 메인 대화 context 를 아끼려고 스스로 판단해 쓴다. 하위 에이전트를 못 쓰는 도구면 같은 역할을 혼자 차례로 밟는다.
team-status팀원 모두의 핸드오프를 모아 누가 언제 무엇을 얼마나 했는지, 미완 작업·TODO·진행 중 브랜치·오래 갱신 안 된 사람을 보고한다. "팀 현황", "다들 어디까지 했어", "누가 뭐 하고 있어" 요청에 쓴다.
ticket이슈·티켓 한 건(장애·결함·QA·UAT 지적·요청)을 영향 범위 → 재현 → 원인 확정 → 수정 → 검증 → 조치 보고 순서로 처리한다. 모든 유형 공통. "티켓 처리", "장애 봐줘", "이 이슈 고쳐줘", "QA 지적 처리" 요청에 쓴다.
tidy방향이 바뀌거나 고친 뒤 남은 파일(안 쓰게 된 코드 · 문서 · 이미지 · 스크립트 · 백업 사본)을 찾아 근거와 함께 보이고, 승인받은 것만 지운다. "정리해줘", "안 쓰는 파일 지워줘", "쓰레기 파일", "이전 버전 정리" 요청, 작업 방향을 바꾼 뒤, 단계 · 핸드오프 보고에 정리 후보가 있을 때 쓴다.
