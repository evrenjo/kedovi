# <프로젝트명> 기획 문서

무엇을 왜 만드는지부터 화면 · 데이터 · API 까지, **메뉴를 위에서 아래로 읽으면 시스템이 이해되게** 둔다.
개발 워크스페이스의 AI 에이전트는 이 repo 를 근거로 일하고, 답변 · 코드 · 이슈에 **ID**(예: `FN-ORD-003`)로 근거를 단다.

## 읽는 순서 (메뉴)

| # | 메뉴 | 폴더 | 내용 |
|---|---|---|---|
| 1 | 개요 | [00-overview/](00-overview/) | 무엇을 왜 · 누가 · 범위 · 핵심 흐름 · 아이디어 정리 · 규모(사용자 · 데이터량 · 증가 · 보존) · 용어 |
| 2 | 시스템 구성 | [10-system/](10-system/) | 서버 아키텍처 구성도(단계별) · 외부 연동 · 서버 사양 |
| 3 | 기능 | [20-features/](20-features/) · [25-policies/](25-policies/) | 요구 목록(한 줄씩) → 영역별 기능 문서(동작 · 수용 기준 · 연결 화면 · API) → 업무 규칙 |
| 4 | 화면 | [30-screens/](30-screens/) | 화면 목록 · 화면 정책 · 스크린샷 (화면의 정본은 프로토타입 `30-screens/prototype/`) |
| 5 | 데이터 · API | [40-data/](40-data/) · [45-api/](45-api/) | 테이블 정의서 · ERD · API 목록과 계약 |
| 6 | 결정 · 미결 | [90-decisions/](90-decisions/) | 결정 기록(상태: 제안 · 확정 · 대체됨) · 미결 목록 |
| 부록 | 원본 | [originals/](originals/) · [md/](md/) | Word · Excel · PPT 원본과 md 사본 |

메뉴 순서는 `docs-site.json` 이 정한다. 문서 사이트는 `kedovi docs build` 가 만든다 (`docs-site/`, 손으로 고치지 않는다).

## 정본은 사실마다 하나

같은 사실을 여러 문서에 다시 쓰면 하나가 바뀔 때 나머지가 낡는다. **사실마다 정본 한 곳에만 쓰고, 다른 문서는 ID 로 가리킨다.**

| 사실 | 정본 | 다른 문서에서는 |
|---|---|---|
| 동작 · 수용 기준 | 기능 문서 (`FN-…`, `AC-…`) | 기능 ID 링크 |
| 기능이 쓰는 컬럼 · 값 출처 · 조건 | 기능 문서의 「저장」 표 | 컬럼 타입 · 설명은 데이터 설계에만 |
| 화면 배치 · 이동 | 프로토타입 (`SCR-…`) | 화면 ID 링크 · 스크린샷 |
| 수치 · 시각 · 코드값 · 테이블 | 데이터 설계 · 업무 규칙 (`POL-…`) | 값을 다시 적지 않고 ID 링크 |
| API 모양 | API 계약 (`API-…`, OpenAPI 가 있으면 그것) | API ID 링크 |
| 결정 | 결정 기록 (`DEC-…`) | 결정 ID 링크 |
| 규모 (사용자 · 데이터량 · 증가 · 보존 · 응답 목표) | [규모 문서](00-overview/scale.md) | 항목 이름으로 가리킨다. 결정은 「전제한 규모」 에 기대는 수치를 적는다 |
| 개수 (테이블 수 · 화면 수 등) | 쓰지 않는다 | 문서 사이트 · 검사 도구가 센다 |

## ID 규칙

| 종류 | 꼴 | 예 | 정의하는 곳 |
|---|---|---|---|
| 요구 | `REQ-<번호>` | `REQ-012` | 요구 목록 |
| 기능 | `FN-<영역>-<번호>` | `FN-ORD-003` | 기능 문서 |
| 수용 기준 | `AC-<영역>-<번호>-<순번>` | `AC-ORD-003-2` | 기능 문서 (기능 번호 + 순번) |
| 업무 규칙 | `POL-<번호>` | `POL-004` | 업무 규칙 |
| 화면 정책 | `POL-UI-<번호>` | `POL-UI-002` | 화면 |
| 화면 | `SCR-<영역>-<번호>` | `SCR-ORD-01` | 화면 목록 |
| API | `API-<영역>-<번호>` | `API-ORD-002` | API |
| 결정 | `DEC-<번호>` | `DEC-007` | 결정 기록 |
| 미결 | `Q-<번호>` | `Q-003` | 미결 목록 |

- 영역은 대문자 2~4자(`ORD` · `MEM`)로 정해 모든 문서에서 같게 쓴다.
- 코드에는 진입점 머리 주석에 `@spec <ID>` 로 한 번 적는다 (화면 컴포넌트 = 화면 ID + 기능 ID, 테스트 = 수용 기준 ID). 개발 워크스페이스의 `kedovi docs trace` 가 대조한다.

## 쓰는 규칙

- **ID 는 한 번 붙이면 바꾸지 않는다.** 번호를 다시 매기지 않고, 폐기한 것은 상태를 `폐기` 로 두고 남긴다 (코드 주석 · 이슈가 이미 인용한다).
- 문서 맨 위에 **상태** (`초안` · `검토중` · `확정` · `폐기`). `확정` 만 개발 근거로 쓴다.
- 결정 · 미결 · 개정 경위는 본문에 쌓지 않는다. 결정은 `90-decisions/`, 정하지 못한 것은 [미결 목록](90-decisions/open-questions.md) 한 곳. 변경 이력은 git 이 남긴다.
- 표 칸은 한두 문장. 흐름 · 구성은 mermaid 그림으로.
- 용어는 [용어집](00-overview/glossary.md) 에 먼저 정의하고 같은 말을 쓴다.

## 원본과 md 사본

AI 에이전트는 Word · Excel · PPT 를 안정적으로 읽지 못한다. 원본은 `originals/` 에, 읽을 수 있는 사본은 `md/` 에 **같은 경로로** 둔다.
원본을 고치면 같은 커밋에서 md 사본도 고친다. 처음부터 md 로 쓰는 문서는 원본이 없어도 된다.
워크스페이스 `workspace.json` 에는 이 repo 를 `"kind": "docs", "mdPath": "md"` 로 등록한다.
