# 기능

> 상태: 초안

요구사항 논의의 결과(요구 목록)와 그것을 동작으로 풀어 쓴 **영역별 기능 문서**를 둔다. 상세 설계를 따로 두지 않는다 (시스템 수준 설계는 [시스템 구성](../10-system/), 데이터는 [데이터 설계](../40-data/)).

| 문서 | 내용 |
|---|---|
| [requirements.md](requirements.md) | 요구 목록: 요구 하나에 한 줄 (ID · 내용 · 출처 · 결정 · 상태) |
| `<영역>.md` | 영역(주문 · 회원 …)마다 한 문서. [_template.md](_template.md) 를 복사해 시작한다 |
| [업무 규칙](../25-policies/) | 여러 기능이 같이 쓰는 규칙 · 기준값 (`POL-…`) |

## 쓰는 법

- ID 꼴은 기획 repo [README](../README.md) 의 「ID 규칙」 을 따른다. 한 번 붙인 번호는 바꾸지도 재사용하지도 않는다.
- 요구 목록의 한 줄이 기능 문서의 한 절(`FN-…`)로 이어진다. 기능 문서의 근거 칸에 요구 ID 를 적는다.
- 수용 기준 하나가 테스트 하나다. 테스트 코드에 그 ID 를 붙인다 (`@spec AC-ORD-003-2`).
- 기능마다 화면 ID · API ID 를 적는다. 화면 · API 가 없는 기능은 「없음」 과 이유.
- 기능마다 「저장」 표(이 기능이 쓰는 스키마.테이블.컬럼 · 값 출처 · 조건 · 기본값)를 둔다. 컬럼 정의는 [데이터 설계](../40-data/)에만 두고 여기는 쓰는 것만, 저장이 없으면 「없음」. 시험의 쓰기 보고서와 `kedovi writes check` 가 대조한다.
